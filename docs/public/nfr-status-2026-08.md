### 目標とのギャップ

**計測バグの修正は実キーで検証済み・正式な$/1,000件判定は依然未測定。** job 187により、`_count_web_searches`修正(billing-authoritativeな`server_tool_use.web_search_requests`ベース)が実際のClaude APIレスポンスに対して正しく機能していることを実データで確認できた——これは「測定手段が整備された」という間接的な確信ではなく、実際に5/5件で正しい値が報告・記録されたという直接証拠であり、目標判定における不確実性の一つが解消された。一方で、job 187は5件の診断行+43件の意図的な水増し行という特殊な構成のジョブであり、**通常の(水増しのない)実データ混合でのブレンド平均$/1,000件の正式測定にはならない**。正式な達成/未達判定には、引き続き修正済みコード・retune後の見積もり定数での、水増しなしの実ジョブ(150件〜1,000件規模)再測定が必要。

### 見通し

- **最優先: 修正デプロイ済み・実キーでの正常動作は確認済み(job 187)。残るのは水増しなしの実データでの$/1,000件再測定。** `job_cost_ledger`(V27で`call_site`/`input_tokens`/`output_tokens`/`web_search_requests`の内訳列を追加済み)をSQLで集計するだけで$/item・Stage4ヒット率の両方を正式に算出できる状態になっている——job 185のようなログgrep頼りの手動補正は今後不要になる想定。
- Stage4のヒット率が構造的な閾値(約16.0%、実測単価ベース)にどれだけ近いか/超えているかを、次回の実測で必ず確認する。超えている場合、Stage4の単価をさらに切り詰める方向ではなく、Stage4呼び出し自体の発火条件(ヒット率)を下げる方向の対策が必要になる可能性が高い。
- `tryReserve` は到着順(FCFS)で予算を消費するため、大規模ジョブの後半でCSV行位置依存の予算枯渇が起き得る(`docs/public/known-limitations.md`に追記済み、未修正)。**加えてjob 186で新たに判明した小規模ジョブでの予算枯渇(アイテム数×$0.005という総枠自体がStage4 1回分にも満たないケースがある)も、同じ`tryReserve`設計の別の側面として記録しておく(未修正、実害は診断作業のみで本番の通常サイズのジョブでは考慮不要な規模だが、少数アイテムのテスト・診断ジョブを組む際は要注意)。**
- 300件ゴールデンセット(精度目標2の基盤)は整備済み(2章)だが、AI階層込みの精度・コストを同時に評価する実測はまだ無い。

#### identified-vs-correct の定義ズレ(実例)

上記2.の「識別できたかと正しく識別できたかは別」という限界は抽象論ではなく、job 167で実際に確認できた誤り・不一致が複数ある:

- **誤ったマッチ(別製品への誤同定)**: `Monday.com Desktop` → `spiceworks:desktop`(誤り)、`SentinelOne Agent` → `trellix:agent`(誤り)、`Fork`(Gitクライアント) → `fork-cms:fork`(まったく別の製品への誤同定)。
- **バージョン系列違い**: `Sublime Text 4.4143` → `sublime_text_3`のCPE(製品は合っているがメジャーバージョン系列が異なる)。
- **プラットフォーム不一致**: Trello・GoToMeeting・LastPass・Pulse Secure Clientで、マッチしたCPEの`target_sw`が`iphone_os`/`android`/`chrome`等になっており、CSV記載の実際のプラットフォーム(デスクトップ/ブラウザ拡張等)と噛み合っていない。

いずれも「IDENTIFIED」として集計されるため、上記93.94%等の識別率には反映されず、正解率を独立して測らない限り顕在化しない誤りである。

#### 確信度分布(job 167、1,000件)

`confidence = 0.95`: 658件、`confidence = 0.60`: 232件、`confidence = 0.50`: 40件。**confidence>=0.95に達しているのは65.8%であり、目標2の文言(95%以上の確度で正しく識別)に照らすと分布の時点で目標に届いていない。** 残る34.2%は0.60または0.50という中程度以下の確信度でIDENTIFIED扱いになっており、これらを「正しく識別できた」側に数えてよいかどうかは、そもそも正解率と無関係に確信度分布だけで疑わしい。

#### 指標の実測値(2026-08-29改訂、指標定義そのものを是正)

**旧「(a) 識別率 = IDENTIFIED / 300」は撤回する。** 300件中32件は意図的に`UNIDENTIFIED`が正解の統制行(架空製品+CPE辞書/OSVレジストリいずれにも存在しない実在製品)であり、これを分母に含めると完璧なシステムでも(300-32)/300=89.33%が理論上限になり、95%という目標そのものと比較不能になる(この構造的な問題はjob 167の93.94%(識別率、930/990)にも当てはまる可能性があるが、母集団の定義が異なるため直接比較はしない)。代わりに以下2指標に分離する(`test-data/compute_golden_300_metrics.py`側の算出ロジックも同日付で修正済み):

| 指標 | 算出式 | 実測値 |
|---|---|---|
| (a) 識別対象recall | IDENTIFIED / 268(300から統制行32件を除いた、本来識別されるべき行の数) | **264/268 = 98.51%** |
| (a-fp) 統制行偽陽性率 | 統制行のうちIDENTIFIEDになってしまった件数 / 32 | **8/32 = 25.00%** |
| (b) 正解率 | 実際の出力(ecosystem/package_nameまたはCPE vendor/product)が期待値と一致した件数 / 298(下記2件を除外後の母数) | **273/298 = 91.61%** |
| (c) 高確信度正解率(厳密) | confidence>=0.95 かつ正解と一致 / 298 | **200/298 = 67.11%** |
| (c') 高確信度正解率(参考、UNIDENTIFIED的中を「確信度を要さない完全一致」として算入) | 上記 + UNIDENTIFIED的中 / 298 | 224/298 = 75.17%(参考値、目標2の文言上は(c)が本命) |

(a)の98.51%だけを見ると目標95%を上回るように見えるが、これは「識別を試みるべき行のうち実際に何か識別が出た割合」であり、**その識別が正しかったかどうかは(b)/(c)が担う**——目標2の文言「95%以上の確度で正しく識別できたか」に対応するのは(c)であり、67.11%と最も低い。(a-fp)の25.00%(32件中8件)も見過ごせない——統制行の4件に1件で、実在するが脆弱性データに紐付かない製品(Chocolatey限定でしか見つからない等)に対して誤って識別済み扱いを返している。

(b)(c)の母数を300ではなく298とした理由: 68件の`IDENTIFIED_CPE`のうち2件(Kibana、Ditto)は、ジョブ実行後にアプリの実際の出力とこのCSVの正解が食い違ったため`test-data/verify_cpe_match_string.py`で追加検証したところ、NVD CPE辞書側の表記自体が本質的に曖昧(Kibana: `elastic:kibana` vs `elasticsearch:kibana`のどちらが現行版に対応するか版数範囲だけでは確定できず、Ditto: 同名の全く別の実在製品〈クリップボード管理ツールのDitto〉と〈Eclipse Foundationの実在プロジェクトEclipse Ditto〉が名前だけでは区別不能)であることが判明し、どちらの判定に倒しても正しい精度を表さないため、採点対象から除外した(識別対象recallの分子・分母両方には引き続き含めている——Kibanaは`IDENTIFIED_CPE`で実出力もIDENTIFIEDのためrecallの分子に、Ditto側は下記(a-fp)の統制行偽陽性の分子に、それぞれ算入される。この算入漏れが上記「三次改訂」で修正した集計バグの内容そのもの)。詳細は`test-data/golden-300.design.md`「Post-run CPE ambiguity findings」に全件開示。

なお、このCSV構築中に本エンジニア自身の正解付与ミスが計7件見つかり、ジョブ実行後に是正した。**算数の再検証(2026-08-29)**: 旧版は「是正前87.7%(263/300)→是正後90.94%(271/298)」と記載していたが、5件の修正+2件の除外という説明とは整合しなかった(268/298=89.93%になるはずで、271との差3件が未説明のまま)。263という数字は是正前の生データを上書きしてしまったため今となっては正確に再現できず、撤回する。代わりに、現在保持しているデータ(現行CSV+job 168の実出力)から効果ごとに切り分けて再構成した、検証可能な計算過程を`test-data/golden-300.design.md`「Correction-effect arithmetic」に記載した。要旨:

| 段階 | 母数 | 正解数 | 正解率 | 内容 |
|---|---|---|---|---|
| 0. 是正前(3種の是正すべて未適用) | 300 | 266 | 88.67% | 出発点(現行状態から3種の是正を逆算して再構成) |
| 1. +ベンダータグ是正5件(Skype/Docker Desktop/Postman/Symantec Endpoint Protection/PDF-XChange Editor—いずれもベンダーが買収・改称された後のバージョンを選びながら買収前の古いCPEベンダー名を正解記載していた) | 300 | 271 | 90.33% | +5正解(job 168の出力は元から正しく、このCSVの正解の方が誤っていた) |
| 2. +除外2件(Kibana、Ditto、母集団から除外) | 298 | 271 | 90.94% | 正解数は不変(両方とも除外前から不正解扱い)、母数が減るだけで精度改善ではない |
| 3. +Blender/Rufus是正2件(後述) | 298 | 273 | **91.61%** | +2正解(job 168の出力は元から正しく、`expected_outcome`が`UNIDENTIFIED`ではなく`IDENTIFIED_CPE`であるべきだった) |

**現在の報告値は91.61%(273/298)。** これは「数字を良く見せるための調整」ではない——各段階の根拠(各ベンダー・プロダクトのCPE辞書内バージョン範囲の実測、Blender/Rufusのページング修正込みの再検証)は`golden-300.design.md`に全件記載しており、是正後も目標の95%には遠く届いていない。

## 7. 信頼性(reliability)

### 現状(コード直接確認)

- `ExternalRegistryRateLimiter.java` / `NvdRateLimiter.java` ともに存在確認(`backend/src/main/java/com/vulncheck/app/service/registry/ExternalRegistryRateLimiter.java`, `backend/src/main/java/com/vulncheck/app/service/nvd/NvdRateLimiter.java`)。エコシステム/サービス単位でのペーシングが実装されている(crates.io 1100ms等)。

- `JobCostBudgetService` のfail-closed挙動を確認: `endedJobIds`(`ConcurrentHashMap.newKeySet()`)によるtombstoneセットが `tryReserve`(`:128`)内でチェックされている。Javadocに「Before this tombstone existed, `endJobBudget` simply removed the budget ... letting any in-flight item's `tryReserve` call fail open — unlimited Claude API spend」と明記されており、アイテム並列化で顕在化したフェイルオープンのバグに対する修正として実装されていることをコードから確認。**訂正: このfail-closedは「常にfail-closed」という意味ではなく、対象が明示的にtombstone化されたジョブIDに限定される、より狭い挙動である。** `tryReserve` は `endedJobIds` に含まれるジョブID(=`endJobBudget` で明示的に終了させたジョブ)に対してのみfail-closed(`false`を返す)。これに対し、`startJobBudget` が一度も呼ばれていない(登録されたことのない)ジョブIDは意図的にfail-**open**する設計になっている(`cap == null` の分岐が `true` を返す、`JobCostBudgetService.java:133-135`)。これはJavadocに明記された意図的な仕様であり、バグではないが、「fail-closedな設計」と一括りに言うのは不正確で、実際の適用範囲(tombstone化された既知ジョブIDのみ)を正しく記述する必要がある。

### 目標とのギャップ

明示的な数値目標はない。レート制限の仕組み、およびコスト予算の(tombstone化されたジョブIDに限定される)fail-closed/(未登録ジョブIDに対する意図的な)fail-open設計は、いずれも「存在し、かつ実装意図通りに配線されている」ことをコードで確認できた。**`StuckJobResumer` については、ジョブ37の3回の中断/再開サイクルにより、実運用条件下での有効性が実測エビデンスとして検証済みとなった(上記参照)。** 一方でレート制限まわりの輻輳耐性、およびコスト予算のfail-open/fail-closedの境界挙動そのものが実際の障害時にどう影響するかは、引き続き実測ログでの検証範囲外。
