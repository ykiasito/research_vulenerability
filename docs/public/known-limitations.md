## 意図的な設計判断（バグではない）

- **コスト予約（`JobCostBudgetService.tryReserve`）は先着順(FCFS)であり、CSV行位置依存の「AI階層飢餓」が実測確認されている（2026-08-29、job 185）**: `tryReserve`はジョブの残り予算に対して到着順に予約するだけで、優先度付けや期待値ベースのランキングは一切行わない（`JobCostBudgetService.java:tryReserve`のjavadoc「Known limitation, not fixed in this pass」に元々明記済み）。150件のjob 185で実際にこれを観測: 150件中53件がAI階層(Tier2/Tier3/Stage4のいずれか)を一度もスキップされずに使えなかった——大規模ジョブほど後半の行がCSV上の並び順というだけの理由で静的識別のみへ縮退する確率が上がる。EVランキング/ペーシング型の入場ポリシーへの変更は別途の設計課題として意図的に見送っている（スコープ外、2026-08-29のコスト目標修正タスクでも対応せず）。
- **ジョブのコスト上限はハードキャップではなく、並列度分だけソフトに超過し得る**: `tryReserve`は各AI呼び出しの**見積もり**額を予約し、実際のClaude API応答が返った後に`reconcile`/`reconcileBundledComponent`が実測額へ差し替える（差額を返金または追加徴収）。見積もりが実測を下回っていた場合（retuneされた定数を上回る外れ値等）、その差額はジョブの残り予算に反映されるのが呼び出し完了後であるため、`itemProcessingExecutor`の並列度(現状8)まで同時に「見積もり通れば予約成立」する呼び出しが走り得る。理論上の最大超過は「並列度 × (実測−見積もり)」であり、ジョブの`COST_CAP_PER_ITEM_USD`ベースの上限額を額面通りの絶対上限として扱わないこと——見積もり定数を実測p95の安全マージン込みで設定する運用（`JobCostBudgetService.java`のコメント参照）で超過幅を実務上小さく保っているだけで、構造的に排除してはいない。ローリング平均方式や再オファー機能への変更は今回意図的に見送っている（スコープ外）。

- **小規模ジョブではAI階層（特にStage4/Tier3）が一度も発火し得ないハードな下限が存在する（2026-08-29、job 186で実測確認）**: ジョブ全体の予算上限は`COST_CAP_PER_ITEM_USD($0.005) × アイテム数N`で決まるため、この総枠自体が1回分の予約額を下回る場合、他の支出が一切なくてもその階層は構造的に一度も発火しない。2026-08-29のコスト定数retune（`JobCostBudgetService.java`のTIER3_WEB_SEARCH_IDENTIFY_COST_USD/STAGE4_WEB_SEARCH_RESEARCH_COST_USDのretune）により、この下限は**Stage4がN≥3→N≥7、Tier3がN≥6→N≥10**へ悪化した（retuneはコスト精度を改善する一方、少数アイテムのジョブではAI階層をより起動しにくくする副作用を伴う。詳細な算数は`docs/public/nfr-status-2026-08.md`1章の項目5節参照）。さらに深刻なのは、この不発火が利用者から見えない形で握りつぶされる点である: `Stage4WebSearchResearchService.research()`（`Stage4WebSearchResearchService.java:57-60`）は予算枯渇時に`return 0`してINFOログを出すだけで、`item.researchIncompleteReason`を一切設定しない。その結果、`templates/jobs/detail.html:94`の判定（`researchIncompleteReason == null`かつ脆弱性0件の場合に🟢「影響なし」と表示）に該当し、「Stage4が予算不足で一度も調査していない」項目が「調査済みで脆弱性0件」と全く同じ見た目で断定表示される——上記のChocolatey項目と同型の「誤った安心感」問題である。今回のコスト目標修正タスクではこの表示問題は未修正・対応スコープ外。将来的な改善案としては、予算枯渇によるスキップ専用の`researchIncompleteReason`値（例: `BUDGET_EXHAUSTED`）を追加し、`SOURCES_FAILED`/`IDENTIFICATION_TOO_WEAK`と同様に画面上で区別表示する形が想定される。

- **依存関係ツリー展開は不採用（2026-08-26評価・見送り）**: CSVに列挙された1パッケージを、その全推移的依存関係へ展開してから調査する方式を検討したが、シニアエンジニアレビューで不採用と判断した。理由は3つ: (a) バージョン範囲の解決は各外部APIのサーバーサイドに委任し、自前のバージョン比較/解決ロジックは実装しないという設計判断（[pipeline.md:45](./pipeline.md)）と正面から矛盾する——依存関係ツリー展開にはエコシステムごとのバージョン範囲リゾルバが本質的に必要になる。(b) このアプリのCSVコーパスの60%はレジストリ非登録のデスクトップソフトウェアであり、展開元となるマニフェスト自体が存在しない。(c) `ExternalRegistryRateLimiter`は全ジョブで共有されるエコシステム単位のレートリミッタであり、推移的解決は同時実行中の他ジョブも巻き込んで待ち時間が青天井になりうる——コストの問題であるだけでなく、スループットの問題でもある。代わりに、既にバージョンが確定した状態のロックファイル/SBOM（`package-lock.json`等）をアップロード時にフラット化してジョブ行に変換する、よりスコープの狭い代替案を採用した。

- **CVE/GHSAエイリアス統合なし**: 同一の実脆弱性を指すCVE-IDとGHSA-IDが両方見つかった場合、別々の行として残る。
- **Stage4はStage2が0件の時、またはヒントのみの時にしか発火しない**: 「影響ある脆弱性が1件でも見つかれば静的調査で完結してよい」という中核方針に基づく。取りこぼし（例: NVDに複数の実CVEがあるが、CPE未紐付けの最新CVEやベンダー独自アドバイザリーは見逃す）が発生し得るが、仕様として許容している。
- **NVDキーワード検索（Stage3）は無効化**: 関連度ソートが無く、一般的な製品名で無関係な大量のノイズがヒットするため。LLMによる関連度フィルタを実装するまで`@Component`を外したまま。
- **同梱パッケージ検知は「精密な判定」ではなく「トリアージ（要確認フラグ）」として意図的に設計している（2026-08-26決定）**: このチェックはCPE/OSVを実際に照会して脆弱性の有無を調べはするが、ユーザー向けの見せ方は「これはCVE-XXXX、深刻度Y、修正版Zです」という断定ではなく、「同梱コンポーネント `名前 バージョン` に既知の脆弱性情報があります。詳細は個別にご確認ください」という、調査を促すだけの控えめな表示にとどめている。ベンダー曖昧解消（CPE辞書上で同じproduct slugを複数ベンダーが持つケース、例: zlibにcloudflare/gnu/zlib自身が並存）で複数ベンダーが候補として残った場合も、精密採点ではなく「該当なし（要確認なし）」として扱う。理由: このアプリの利用者にとって同梱パッケージ調査は本来優先度が低く、正確な追跡自体が難しい領域であるため、自信満々に間違った断定をするより、無難な「疑わしきは沈黙」を選ぶ方針とした。同じ理由で、CSVエクスポートの`bundled_component_findings`列も個々のCVE IDを列挙する完全な監査証跡ではなく、コンポーネント名・バージョン単位の存在フラグにとどめている。
- **同梱パッケージ検知: オプトインしたが変更履歴が見つからなかった項目は「異常なし」と見分けがつかない**: `BundledComponentResearchService`は、対象製品の公式チェンジログ/リリースノートをAI Web検索で発見できなかった場合（`found=false`）、その項目に対して何も永続化せず終了する。ユーザーがこの機能にオプトインし、コストも支払ったにもかかわらず、実際には同梱パッケージの調査が一切実行されなかった項目は、調査した上で何も見つからなかった項目と画面上まったく同じに表示される——他の箇所で`researchIncompleteReason`が防いでいるのと同じ「偽陰性が『クリーン』に見える」形の問題が、この機能には存在する。2026-08-26のシニアレビューで指摘済みだが、意図的に対応を見送っている（スコープ外）。

- **GHSA/OSVが「メタパッケージ」に対して大量の脆弱性を返すことがある（依存解析はしていない）**: 例えば`symfony/symfony`（Symfonyの全コンポーネントを束ねるメタパッケージ）を照会すると、`symfony/yaml`・`symfony/mime`等、個別コンポーネントのCVEも大量にヒットする。これは本アプリが依存関係を解析しているのではなく、**GHSA自身のアドバイザリーデータが元々そう登録されている**ため（例: GHSA-9frc-8383-795mは`composer symfony/yaml < 5.4.52`と`composer symfony/symfony < 5.4.52`を独立した`vulnerabilities[]`エントリとして両方リストしている — `https://api.github.com/advisories/{id}`で確認可能）。Symfonyのセキュリティチームが「メタパッケージ経由でインストールしたユーザーも見逃さないように」意図的に両方へ登録している運用。2026-08-23、`symfony/symfony`のPackagist登録テスト時に発見・確認。

- **GHSAミラー実装（2026-08-27）: `VersionUtils`のプレリリース順序の弱点が`GhsaVersionRange`のfail-closedルールの直接の根拠**: `VersionUtils.compare()`はセグメントを`[._+\-]`で分割する単純な実装のため、`1.0.0-rc1`のようなプレリリースサフィックス付きバージョンを正しい意味論で比較できない（`1.0.0-rc1 > 1.0.0`という誤った結果になる）。`GhsaVersionRange`はアイテムのバージョン・範囲の上下限のいずれかが「プレーンなドット区切り数値」（`^\d+(\.\d+)*$`）としてパースできない場合、範囲評価そのものを棄権する（何も所見を出さない、「対象外」を「安全」として扱わない）——プレリリース版を使っているアイテムに対しては、GHSAミラー由来の所見が体系的に出ない（fail-closedの副作用として許容）。この制約はGHSAミラー導入前から`VersionUtils`自体に存在していたものであり、GHSAミラー実装がそれを可視化・記録した形。
- **GHSAミラー実装（2026-08-27）: `cvss_score`は常にNULL**: GHSAのOSVスキーマ`severity[]`は生のCVSSベクター文字列のみを持ち、CSAFの`cvss_v3.baseScore`のような事前計算済み数値スコアを持たない。ベクター文字列から数値スコアを算出するパーサは本フェーズのスコープ外——`severity`（テキスト列）は`database_specific.severity`（LOW/MODERATE/HIGH/CRITICAL）から取得している。
- **GHSAミラー実装（2026-08-27）: `ghsa_affected_versions`（個別バージョン列挙）は実データではほぼ未使用**: 実装時にgithub-reviewed advisoryを多数サンプリングしたが、`affected[].versions[]`を独立に埋めている実例は一件も見つからなかった（レンジのみで表現されている）。スキーマ・パーサ・照合ロジックは仕様通り実装済みだが、`GhsaDocumentUpsertServiceTest`のこの経路のテストフィクスチャは実際にキャプチャした文書ではなく、スキーマ形状のみを検証する手書きの合成フィクスチャである。
- **OSV.devミラー設計検討（2026-08-28）: OSV.dev版のGHSAレコードは`affected[].versions[]`を完全列挙しており、上記の「ほぼ未使用」評価を精緻化する必要がある**: 同一アドバイザリ`GHSA-m452-q8c9-rg2f`をGitHub版（現行`ghsa_advisories.raw_json`、3,446バイト）とOSV.dev版（`Maven/GHSA-m452-q8c9-rg2f.json`、5,243バイト、52%大きい）の両方で実測比較したところ、差分の正体は`affected[].versions[]`の完全なバージョン列挙（`2.1.0-RC1`・`3.0.0.Beta1`等のプレリリース版を含む）だった——つまりGitHub版のAPIレスポンスにはこの列挙がほとんど現れない一方、OSV.dev版には存在する。実DB上`ghsa_affected_versions`が2,803行しかない（34,784件のアドバイザリに対して1件あたり平均0.08行）という実測は、この「GitHub版のGHSAレコードでは`affected[].versions[]`がほぼ空である」という傾向と整合する。OSV.dev版のGHSAレコードを取り込めば、`OsvVersionRange`（旧`GhsaVersionRange`）の数値限定fail-closed制約（本ファイルの上記項目参照）をプレリリース版アイテムについて回避できる可能性がある——`^\d+(\.\d+)*$`でパースできないバージョン境界であっても、`affected[].versions[]`の個別完全一致であれば評価可能なため。**ただし今回はこの情報を取り込んでいない**——OSV.dev版の`GHSA-*.json`をOSVミラー側にも取り込むことは明示的に見送っており（GHSAアドバイザリーは`GhsaSyncService`側のGitHub由来データに一本化する現行方針を維持）、将来的に`GhsaSyncService`の供給元をOSV.dev側へ切り替えるバックログ項目の中で改めて検討することになる。
- **GHSAミラー実装（2026-08-27、シニアレビュー項目9）: `fixed_version`は1 CVEにつきグローバル1値だが、実際の修正版はパッケージ単位の答えである**: `vulnerabilities.fixed_version`列は1つのCVE行につき1つのグローバル値しか持たないが、同一CVEが複数の異なるパッケージに影響し、それぞれ別の修正版を持つケースが実在する（実測: CVE-2020-13935は`org.apache.tomcat:tomcat`の修正版が7.0.105、`org.apache.tomcat.embed:tomcat-embed-websocket`の修正版が10.0.0-M7——100件の実文書サンプルで約7%の頻度で観測）。この場合、どのソースの書き込みが後に共有行へ着地するかによって値が上書きされ、無関係なアイテムが別パッケージの修正版を見てしまい得る。これはGHSA導入前からNVD/OSVに既に存在していた既存の欠陥であり、GHSAミラーが新たに持ち込んだ問題ではない——既存の欠陥の対象にGHSAも追加されただけ、という位置づけが正確な理解。**本タスクでは対応しない**——将来的な修正案としては、`job_item_vulnerabilities`にアイテム単位の`fixed_version`列を追加し、`JobController#highestFixedVersion`がグローバル列より優先してそれを参照するよう変更する形が想定される。
- **GHSAミラー実装（2026-08-27、シニアレビュー項目10）: パッケージ名の小文字化を設計文書の指定範囲より広く適用している**: `GhsaPackageNameNormalizer`の一律小文字化は、設計文書が明示的に指定していたnpm/PyPI/NuGet/Mavenの4エコシステムを超えて、go/rubygems/crates.io/packagist/hex/pubにも適用している。Goについては、Goのモジュールパスは本来大文字小文字を区別する仕様であるため、これは意図的な「広げすぎ」のトレードオフとして受け入れている（稀だが実在する偽陽性拡大のリスクを承知の上での意図的決定であり、見落としではない）。
- **GHSAミラー実装（2026-08-27、シニアレビュー項目10）: `GhsaVulnerabilitySource#find`のfail-closed／評価不能ケースが「該当なし」と区別できない**: エコシステム非対応やパッケージ名欠落などでバージョン照合そのものができない場合、`find`は`SourceResult.success(List.of())`を返す——これは「実際に照会したが何も見つからなかった」ケースと下流からは区別がつかない（`GhsaVersionRange`自身のjavadocはこの扱いをしないよう明記しているにもかかわらず）。`anySourceSucceeded`はこの区別を用いて有料のStage4 AIフォールバックを発火させるかどうかを判断しているため、実際には「未評価」であるにもかかわらず「評価済み・所見なし」として扱われ、Stage4フォールバックが発火しない可能性がある。本タスクでは専用の「評価不能」を表す戻り値型は実装しない——将来の課題として記録するのみ。
- **Chocolatey限定の識別は「調査済みで脆弱性0件」と「そもそも一度も調査されていない」を利用者が区別できない、誤った安心感を生む(2026-08-29、golden-300ベンチマークで確認)**: `ChocolateyRegistryClient`はCPE辞書にもOSVの10エコシステムにも紐付かない11番目のレジストリだが、Chocolatey限定で一致した行は他の識別済み行と全く同じ見た目で`status=IDENTIFIED`・`confidence=0.95`(`VERSION_CONFIRMED_CONFIDENCE`)として画面に表示される。実際には脆弱性データの照会経路(CVE/GHSAフィードもCPEマッチングも)が一切無いため、そのアイテムについて脆弱性の有無は何も分かっていない——にもかかわらず、非エンジニア向けGUIの利用者からは「調査済みで脆弱性0件」なのか「識別に失敗し何も調査されていない」なのかが画面上区別できない。`golden-300.csv`の統制行(本来`UNIDENTIFIED`が正解の実在製品)32件中7件で実際に観測されている(Slack・OBS Studio・WinDirStat・WizTree・ShareX・ClipboardFusion・XYplorerがchocolatey経由でIDENTIFIED扱いになる)。

- **クロスレジストリの同名衝突をusage_textでタイブレークする(2026-08-29実装、`Stage1IdentificationService#maxConfidenceMatch`)**: 複数レジストリに同名パッケージが存在し(numpy/jekyll/redis/phoenix/phoenix_live_view/http等)、AI裁定が使えない(予算枯渇・未設定)場合、従来は`REGISTRY_MATCH_TIE_MARGIN`(0.05)以内で並ぶ候補のうち到着順で選ばれ、golden-300実測で6件の誤ルーティングを引き起こしていた。`item.usage_text`を`ECOSYSTEM_USAGE_TEXT_KEYWORDS`(単語境界付き正規表現でマッチさせる、複数文字の保守的なキーワードのみ——「go」「pub」のような1〜2文字の単語は他の英単語の部分文字列として誤検知するため採用していない)で照合し、タイの中でちょうど1エコシステムだけusage_textが一致した場合に限りそちらを採用する。0件または2件以上一致する場合は従来通り最大confidenceの候補のまま——単一の明確な勝者が既に存在するケース(タイが発生しない大多数のケース)には一切影響しない、既存の挙動を狭めるだけの追加ロジックである。

- **`part=o`(オペレーティングシステム)CPEを、`part=a`(アプリケーション)候補が候補プールに1件も無い場合に限りフォールバックとして含める(2026-08-29実装、`Stage1IdentificationService#rankCpeCandidates`)**: Cisco IOS XE・PAN-OS・MikroTik RouterOSのように、NVDが`part=a`エントリを持たず`part=o`としてのみカタログしている実在製品を救済するための限定的なフォールバック。`part=a`候補が1件でも存在すれば常にそちらが優先され、このフォールバックは一切発動しない構造になっているため、以前のインシデント(ハードウェアCPEが実在するソフトウェア候補を押しのけた事故——`part=a`候補が存在するのに無関係な`part=h`候補が勝ってしまった)を再現する余地が構造的に無い。`part=h`(ハードウェア)は状況に関わらず除外したまま変更していない。

- **高確信度AI検証バックストップ(`HighConfidenceVerificationService`、既定OFF)**: Stage1がTier1静的ロジックのみ(レジストリ+CPE辞書、AI不使用)で到達した高確信度(既定0.95以上)CPEマッチを、Tier2/Tier3のAI裁定を一度も経ていないまま`IDENTIFIED`にしてしまう「確信度貸与」ギャップ(golden-300で実際の誤CPEがこの母集団に集中していた)への事後バックストップ。AI+web_searchで該当CPEのvendor/productが妥当かどうかを再検証し、`CONFIRMED`/`INCORRECT`/`AMBIGUOUS`の3値で判定する——`AMBIGUOUS`は「間違っている」のではなく「複数の妥当な候補があり確定できない」ことを示す別カテゴリで、確信度・CPEは変更せず人間レビュー用のフラグ(`verification_status`/`verification_note`)のみを立てる。`INCORRECT`はCPEを常に削除して確信度を`downgrade-factor`(既定0.5)倍するが、削除後にレジストリ由来の裏付け(ecosystem)が残っていなければ、確信度がどれだけ残っていても常にUNIDENTIFIED相当(行削除)まで完全に demote する(確信度が下がりきらない設定でも脆弱性照会経路が無いIDENTIFIEDを作らないようにするための修正で、当初存在した設定可能な`demotion-floor`は撤廃した)。
  - **既定で無効**(`app.high-confidence-verification.enabled=false`)——有効化しない限り既存の挙動・コストに一切影響しない。
  - 専用のコスト台帳を持つ(`JobCostBudgetService#reconcileVerification`、`app.high-confidence-verification.cost-cap-per-item-usd`は既定0=事実上使えない)——既存のMAIN予算(Tier2/Tier3/Stage4)とは独立して消費される。1つの理由: job 191実データで108/300件がこの検証の対象になり得ると判明し、その需要($3.78相当)が300件ジョブ自身のMAIN予算($1.50)の2.5倍に達した——MAIN予算を共有する設計だと、この機能を有効化しただけでジョブ冒頭の行がAI予算を独占し、後続の全アイテムのTier2/Tier3を飢餓状態にしかねない(`JobCostBudgetService#verificationCostCapPerItemUsd`のjavadoc参照)。
  - 関連設定キー: `app.high-confidence-verification.enabled`/`confidence-threshold`(既定0.95)/`downgrade-factor`(既定0.5)/`cost-cap-per-item-usd`(既定0)——対応する`HIGH_CONFIDENCE_VERIFICATION_*`環境変数は`docker-compose.yml`参照。

- **同期ジョブの排他制御はDBカラムではなくプロセス内メモリのフラグで行っている**: `GhsaSyncService`・`SiemensCsafSyncService`・`RedHatCsafSyncService`・`OsvSyncService`はいずれも`AtomicBoolean running`フィールド（`GhsaSyncService#running`・`SiemensCsafSyncService#running`・`RedHatCsafSyncService#running`・`OsvSyncService#running`）を持ち、同期開始時に`running.compareAndSet(false, true)`で排他を取っている。`ghsa_sync_state.sync_in_progress`等のDBカラムは`/admin`画面向けの観測用であって、実際の排他制御には使っていない。これは意図的な設計判断——このアプリは単一インスタンス運用を前提としており、複数インスタンスでスケジューラが同時に走る構成には元々対応していない。DBフラグを排他制御の主体にすると、クラッシュ後にフラグが`true`のまま残って以後の同期が永久に止まる懸念があり、それよりプロセス内蔵のガードの方が安全という判断による。

- **OSVミラー実装（2026-08-29、A/B検証ゲート・実データ深掘りの結果、ゲート通過・`@Component`切り替え済み）**: 前回記録（初回10件のA/B検証）の実データ深掘りで、切り替え前に直すべき実装バグ2件が新たに見つかり、いずれも修正済み。(1) **P0: `introduced`センチネル値の正規化不足**——`OsvDocumentUpsertService#parseRangeEvents`（旧実装）は`introduced:"0"`だけをnullへ正規化しており、RustSecが慣用する`"0.0.0-0"`（および`"0.0.0"`）は生の文字列のまま`osv_affected_ranges.introduced_version`へ格納されていた。`OsvVersionRange.matches()`は`^\d+(\.\d+)*$`にマッチしないバージョン境界をfail-closedで棄権するため、`"0.0.0-0"`はハイフンを含み非マッチ——結果として、crates.io（RustSec）は`osv_affected_versions`が常に0件で範囲照合が唯一の照合手段であるにもかかわらず、advisory単位の到達率が実測19%（233/1,207）まで落ちていた。修正: `"0"`・`"0.0.0"`・`"0.0.0-0"`の3値すべてを等価にnullへ正規化（`isZeroSentinel`ヘルパー、意味論上どれも「最初のバージョンから」で範囲を狭めないため誤検知リスクはゼロ）。`vulncheck_test`への再同期で到達率19%→97.3%（1,174/1,207、想定していた約95%を上回った）まで回復を実測確認。(2) **P1改善: severityのCOALESCE補完**——OSV自身の`database_specific.severity`は実測0/13,682件で常に空だったが、`OsvVulnerabilityLookupRepository`の2クエリを`COALESCE(o.severity, g.severity)`に変更し、既にLEFT JOIN済みの`ghsa_advisories.severity`から追加コストゼロで補完するようにした——severity付与率0%→85.4%（11,679/13,683）を`vulncheck_test`で実測確認。
- **OSVミラー実装（2026-08-29、上記修正後の拡大A/B再検証、31件・crates.io/go厚め）: `OsvVulnerabilitySource`（ミラー版）を`@Component`化し、Stage2の実配線に切り替え済み——`OsvLiveVulnerabilitySource`（ライブAPI版）は削除済み**。修正後、crates.io/goを厚めにした31件の実(ecosystem, package, version)組でライブ版とミラー版の`find()`所見IDを再度突き合わせたところ、依然「ライブ版にしか出ない所見」は多数見つかったが、内訳を追跡した結果、実質的な取りこぼしはゼロと判断した（データベースの生データを直接突き合わせて個別に確認済み）: (1) **ID表記の違い**——ライブAPIはOSVレコード自身のネイティブID（`RUSTSEC-*`/`GO-*`/`PYSEC-*`等）をそのまま返すのに対し、ミラー側は`COALESCE(o.cve_id, g.cve_id, o.ghsa_id, o.osv_id)`によりCVE-ID（無ければGHSA-ID）を優先して発行するため、同一アドバイザリーが別ラベルで現れる（例: `RUSTSEC-2020-0071`のcve_id/ghsa_id列を直接確認し、ミラー側の`CVE-2020-26235`と同一行であることを確認済み）。(2) **同じくID表記の違いが、GHSAミラー側`GhsaVulnerabilitySource`との比較でも再現**——ライブAPIが返す`GHSA-*`由来所見の多くも、ミラー版のOSV/GHSA双方がCVE-ID優先で同一アドバイザリーを別ラベル発行しているだけで、Stage2の合算結果に実害はない（例: `npm/lodash@4.17.15`のライブ側`GHSA-29mw-wpgm-hmr9`はGhsaVulnerabilitySource側で`CVE-2020-8203`として同時に検出されている、既知のlodashプロトタイプ汚染CVE）。(3) **`OsvVersionRange`のfail-closedルールによる既知の制約（go pseudo-version等、下記の残課題）**——件数は少なく、影響は限定的。**この再検証結果を受けてsenior-reviewerが判断し、`OsvVulnerabilitySource.find()`をStage2の実配線へ切り替え、`OsvLiveVulnerabilitySource`は削除した**（2026-08-29）。実devDB（`vulncheck`）にもV25マイグレーション適用・baseline同期（13,683件取り込み）を実施済み。
- **【残課題、今回のスコープ外】goのpseudo-version・`+incompatible`形式の正規化は未対応**: `GO-2023-1737`（`go/github.com/gin-gonic/gin`）の`introduced:"1.3.1-0.20190301021747-ccb9e902956d"`のようなGoモジュールのpseudo-version、および`vX.Y.Z-0`・`+incompatible`形式のバージョン文字列は、`OsvVersionRange`の`^\d+(\.\d+)*$`限定fail-closedルールにより引き続き範囲評価を棄権する（crates.ioの`0.0.0-0`センチネルとは異なり、これらは実際に意味のある任意精度の識別子であり、単純な定数正規化では対応できない）。今回のP0修正（センチネル値の正規化）はこの制約を解消しない——影響はgoエコシステムの一部advisoryに残ったままであり、これは新規のバグではなく、`VersionUtils`のプレーン数値限定という既存の設計上の制約（本ファイル上記のGHSAミラー実装の記録と同一の根本原因）が再確認されたもの。将来対応する場合は専用のGoモジュールバージョン比較ロジックの実装が必要。

### `vulncheck_test` ロール・データベースのセットアップ手順

`mvn test`を実行するには、稼働中のPostgresに対して事前にこの専用ロール・データベースを作成しておく必要がある。手順は以下の通り(2026-08-29、稼働中DBの実際のロール属性・グラント内容を`\du`・`pg_roles`・`\dn+`・`pg_database.datacl`で読み出して確認したものであり、推測ではない)。**Postgresコンテナ内で`psql`から実行すること**(`docker exec -it <postgresコンテナ> psql -U vulncheck -d vulncheck`)。

```sql
-- 1. テスト専用ロールを作成(LOGIN以外の特別な属性は付与しない — SUPERUSER/CREATEDB/CREATEROLEいずれもfalseのまま)
CREATE ROLE vulncheck_test WITH LOGIN PASSWORD '<ローカル開発専用の固定値、backend/src/test/resources/application.ymlのコメント参照>';

-- 2. テスト専用データベースを作成(所有者は本番ロールvulncheckのまま — vulncheck_test自身をDB所有者にしない)
CREATE DATABASE vulncheck_test OWNER vulncheck;

-- 3. vulncheck_testロールがこのDBへ接続できるようにする
GRANT CONNECT ON DATABASE vulncheck_test TO vulncheck_test;

-- 4. public スキーマでのテーブル作成(Flywayマイグレーション実行に必要)・参照を許可
--    (vulncheck_test データベースに接続してから実行すること)
\c vulncheck_test
GRANT USAGE, CREATE ON SCHEMA public TO vulncheck_test;

-- 5. 【必須】本番vulncheck・postgresデータベースへのPUBLIC経由の接続を遮断する
--    PostgreSQLはデフォルトでdatacl(データベースACL)がNULLの場合、PUBLICロールにCONNECT/TEMP権限を
--    暗黙付与する。これを塞がないと、上で作ったvulncheck_test(パスワードは`backend/src/test/resources/application.yml`
--    のコメントに記載の固定値)が本番vulncheckデータベースへ接続でき、テーブル自体は読めなくてもカタログ全体
--    (テーブル名・列名・ロール名・pg_settings)の列挙や無制限の一時テーブル作成(10GB上限に対するディスク
--    枯渇リスク)が可能になってしまう(2026-08-29、senior-reviewerが実測・指摘)。
REVOKE CONNECT ON DATABASE vulncheck FROM PUBLIC;
REVOKE CONNECT ON DATABASE postgres FROM PUBLIC;
```

実行後、以下のSQLで`f`(接続不可)が返ることを確認すること:

```sql
SELECT has_database_privilege('vulncheck_test', 'vulncheck', 'CONNECT');
```

**警告: `vulncheck_test`のパスワードは固定値であり(値は`backend/src/test/resources/application.yml`のコメント参照)、`backend/src/test/resources/application.yml`にそのまま平文で書かれている。本番`vulncheck`データベースに到達できる環境で、このロール・パスワードの組み合わせを作成してはならない。**上記手順5のREVOKEを省略した場合、このロールは本番データベースへの偵察・DoS(一時テーブルによるディスク枯渇)の経路になる。ローカル開発専用のPostgresインスタンス(このリポジトリの`docker-compose.yml`が起動するもの)以外では、このロールを作成しないこと。

**トラブルシューティング: 既存テーブルの所有者が`vulncheck`ロールのままで、Flywayマイグレーションが`must be owner of table X`で失敗する場合(2026-08-29、V31適用時に`cpe_dictionary`で発生)**: 通常のFlywayマイグレーション(アプリが`vulncheck_test`ロールで接続して`CREATE TABLE`する)経由で作られたテーブルは`vulncheck_test`所有になるため、この問題は本来起きない。実際に発生するのは、`pg_dump`/`psql`による復元や手動DDLを`vulncheck`(スーパーユーザー)接続で直接実行した場合など、Flyway/vulncheck_test経路の外でテーブルが(再)作成されたケースに限られる。発生した場合は`vulncheck`スーパーユーザーで`vulncheck_test`に接続し、対象テーブルごとに`ALTER TABLE <table> OWNER TO vulncheck_test;`を実行して復旧する。新規Flywayマイグレーションとしての解消は意図的に避ける——本番`vulncheck`データベースには`vulncheck_test`ロールが存在しない(存在してはならない)ため、同じマイグレーションが本番適用時に`role "vulncheck_test" does not exist`で失敗し、本番のDDL反映自体を止めてしまう。2026-08-30時点で`vulncheck_test`内の全31テーブル(および全リレーション)が`vulncheck_test`所有であることを確認済み。
