## 1. 【最優先・要ユーザー承認】暗号化キー配線の欠落 — git初回コミット前に必ず確認すること

**解消済み(2026-08-28)**: 本節が指摘する暗号化キー配線の欠落は、2026-08-28のキーローテーションと`docker-compose.yml`配線修正により解消済みである。`APP_SECRET_ENCRYPTION_KEY`は`docker-compose.yml`の`backend`サービスの`environment:`ブロックへ配線され、`application.yml`のハードコードされたデフォルトリテラルも撤去されて`SecretEncryptionService`が起動時にfail-fastする方式へ変更されている(§2項目4bの完了)。以下の本文は当時の発見内容の記録であり、現状のコードベースの記述ではない。

**これは本ドキュメント全体の中で最も安全性に関わる発見であり、他のどの項目より先に読まれるべきものである。**

### 1-1. 何が起きているか（直接確認済み）

- `.env.example`は`APP_SECRET_ENCRYPTION_KEY`・`ADMIN_EMAIL`・`JOB_RETENTION_DAYS`の3変数を文書化しており、`backend/src/main/resources/application.yml`もこれらを読み込む設計になっている（当時の行番号: `secret-encryption-key`が`:36`、`admin-email`が`:42`、`job-retention-days`が`:45`。現在の行番号はそれぞれ`:39`・`:45`・`:48`、後続の編集でずれている）。
- しかし**この3変数のいずれも`docker-compose.yml`の`backend`サービスの`environment:`ブロックには渡されていない**。同ブロックに存在するのは`SPRING_DATASOURCE_URL`/`SPRING_DATASOURCE_USERNAME`/`SPRING_DATASOURCE_PASSWORD`と`CPE_FULL_SYNC_ON_STARTUP`のみである（`docker-compose.yml`の`backend.environment`を直接確認）。
- 結果として、`.env`にこれらの値を設定してもコンテナには一切伝わらず、実際に使われる暗号化キーは`application.yml`（当時`:36`、現`:39`）にハードコードされたdev用デフォルトリテラル（`app.secret-encryption-key: ${APP_SECRET_ENCRYPTION_KEY:<committed-default>}`）である。有効な上書き経路が存在しない。
- これは`docs/spec/nfr-status-2026-08.md`5章（セキュリティ姿勢）が既に指摘していた内容だが、本ドキュメント作成にあたり改めて直接スポットチェックで再確認した。
- **意味するところ**: 現在DB (`user_secrets`テーブル)に保存されている全ユーザーのAPIキー（Claude/NVD）は、このハードコードされたデフォルトキーでAES-256-GCM暗号化されている。もしこのままgit initして最初のコミットを作れば、**そのリテラルがgit履歴に平文で残る**——後からファイルを消しても履歴には残り続ける。
- 一方、真正の認証情報混入についてはgrepで別途確認済み: `sk-ant-*`・`AKIA*`等の実クレデンシャルパターンをツリー全体で検索したが、該当は全てテストフィクスチャ/ドキュメント上のプレースホルダであり、実キーの混入はない。`.gitignore`は既に`.env`を正しく無視している。**問題は実キーの漏洩ではなく、暗号化キーという「鍵の鍵」がハードコードされたまま履歴に刻まれることである。**

### 1-2. なぜこれが「ユーザーの明示的な承認」を要する事項か

`feedback_stop_for_credentials`メモリの方針（「認証トークン系が必要であれば止まってください」）に照らすと、暗号化キーのローテーションは以下の理由でこの方針の対象そのものである:

- 暗号化キーを変更すると、**既存の暗号化済みAPIキー（DB上の`user_secrets.encrypted_key`）は新キーで復号できなくなる**。
- 選択肢は2つ、どちらもユーザー側の判断が必要:
  - **(a) 既存行を再暗号化する**: 旧キーで復号→新キーで再暗号化するワンショットのマイグレーション/管理操作が必要。実装コストはあるが、ユーザーの手入力を求めない。
  - **(b) 既存ユーザーにAPIキーの再入力を求める**: 実装は単純（単に鍵を変えて古い行を無効化扱いにするだけ）だが、ユーザー体験上の後退。
- どちらを選ぶか、またいつ実行するか（git初回コミットの前か後か）は、本ドキュメントの範囲外の判断であり、**§2項目4b実行前に必ずユーザーへ確認する。**
- なお、Postgresのポート絞り込みや再起動ポリシー、Dockerログドライバのキャップなど（§2項目4a）はこの判断を必要としない——4aは4bの判断を待たずに独立して進めてよい。

### 1-3. git initとの時系列上の関係（重要）

§2項目1（git init）は現ツリーの状態（=暗号化キーが未ローテーションのハードコード値）のまま実行しても、**それ自体が新たな漏洩を生むわけではない**（今のリテラルはdev用ダミー値であり、実運用中のクレデンシャルそのものではない——ただし「このリテラルが本番の実質的な鍵として使われ続けている」という事実自体が問題であることに変わりはない）。したがって:

- git initを暗号化キーのローテーション完了まで待つ必要は**ない**（ローテーションは別スレッドとして並行/後続で進めてよい）。
- ただし、**§2項目4b（docker-compose.yml修正でキーを配線可能にすることと、鍵ローテーション本体）を実行する前に、必ず上記(a)/(b)の判断をユーザーに仰ぐ**——配線を直しただけで実際のキー値をまだ決めていない状態で見切り発車すると、「.envさえ設定すればローテーションできる」と誤解したまま放置される典型的な罠になる（`docs/spec/nfr-status-2026-08.md:117`が既に指摘した罠と同型）。

## 2. 優先順位付き実行計画（本ドキュメントの本体）

以下は**推奨される実行順**であり、承認前に実行してよいという意味ではない。各項目に「完了の定義」を付す。

**実行順序について（並び替えの根拠）**: 本節の項目順は旧版（CI/CDが4番目だった版）から変更した。CI/CDを項目2（git initの直後）へ繰り上げたのは、この順序を強制する技術的制約が元々なかったことに加え、CIが約309件のテストという安全網であり、その安全網は本節で最もリスクの高い2つの変更——項目4bのfail-fast起動チェックと項目5のFlyway migration——が入る**前に**存在しているべきだからである。安全網を後から足すのではなく、リスクの高い変更が来る前に安全網を用意しておく、という順序を意図的に選んだ。

### 項目1: git init・初回コミット・タグ付け

**内容**:

2. `.gitignore`に安全側の追加: `.claude/settings.local.json`（ローカル権限設定、個人環境依存）、`.playwright-mcp/`（MCPのキャッシュ/生成物ディレクトリ）、**`logs/`**（Logbackのローテーション済みアーカイブファイル）。既存の`.gitignore`は`.env`と`*.log`を無視済みだが、**`*.log`パターンはLogbackが生成するローテーション済みアーカイブにはマッチしない**——直接確認したところ、現状`logs/`配下には`.gz`アーカイブが3件（`logs/backend/backend.log.2026-08-25.0.gz`ほか、計約600KB）とアクティブなログが1件（約1.9MB）存在し、いずれも現在の`.gitignore`では無視されない。この状態でgit initすると、運用ログが最初のコミットからgit履歴に永久に焼き付くことになり、これは本節冒頭で述べた「履歴に残せないものは残さない」という§1自身の前提と正面から矛盾する。したがって`*.log`ではなく`logs/`ディレクトリ自体を`.gitignore`に追加する。**なお、これらのログファイルは（bind mountの結果として）root所有になっており、削除・移動などの管理操作には`sudo`が必要**。
3. `git status`で`.env`が無視されていることを目視確認してから`git add`。
4. ブランチモデル: **トランクベース**（単独ユーザーのため）。gitflowのような複数の長期ブランチは導入しない。リスクのある変更のみ短命ブランチを切り、完了後trunk（`main`）へマージする。マイルストーンにはタグを打つ。
5. 初回コミットに`v0.8.0`のタグを付与する（§0のバージョン評価に対応）。

**完了の定義**: `git log`に初回コミットが1件存在し、`git tag`に`v0.8.0`が存在し、`git status`が`.env`・`.claude/settings.local.json`・`.playwright-mcp/`・`logs/`をいずれも追跡外として扱い（`git status --porcelain`が`logs/`配下について何も出力しない）、ルート直下に`resume.txt`・`cap-*.png`・`jobs-*.png`が残っていない状態。

**位置づけ**: シニアレビューの原評価では「今日中に、ユーザー自身の作業として」実施する30分程度の機械的作業であり、本ドキュメントが扱う「計画」というよりは前提整備に近い。ただし後続の全項目（CI/CD含む）はgitリポジトリの存在を前提とするため、実行順としては最初に置く。

### 項目3: Postgresバックアップ/リストア手順の確立 — コンテナ再作成・マイグレーション実行前に必須

**内容**:
1. `pg_dump`でホスト側にダンプを取得する。コンテナ再作成（項目4）やマイグレーション適用（項目5）の直前に、その都度実施する。
2. 取得したダンプを、使い捨てのスクラッチコンテナへ**実際にリストアして検証する**——リストアを試していないダンプはバックアップとして数えない。
3. **重要**: 鍵ローテーション（§2項目4b）前に取得したダンプは、`user_secrets`テーブルの行がローテーション前の暗号化キーで暗号化された状態のまま含まれる。ダンプ取得時にどの鍵世代（key generation）に対応するかを記録しておかないと、将来そのダンプから復元した際に復号不能な`user_secrets`行が静かに生成される。

**優先度の根拠**: CPE dictionaryのフルシンクはゼロから再構築すると数時間かかる（§0参照）が、それでも「再構築可能」ではある。一方`user_secrets`はそもそも定義上再構築不能——アップストリームの一次情報源が存在しないため、失えばそのユーザーにAPIキーを再入力してもらう以外に復旧手段がない。この非対称性から、バックアップ/リストア手順の確立を、稼働中コンテナへ実際に触れる作業（項目4・項目5）より前に置く。

**完了の定義**: ホスト上に`pg_dump`によるダンプ取得手順（コマンド、鍵世代の記録方法込み）が確立し、そのダンプを空のスクラッチコンテナへ実際にリストアしてデータが読めることを最低1回確認済み。

### 項目4: docker-compose.ymlハードニング / シークレット配線 — 「4a: ゲート不要」と「4b: 要ユーザー承認」に分離

§1で述べた通り、鍵ローテーションの実行タイミング・再暗号化方針はユーザーの明示的な承認が必要。しかし、この項目にまとめて含まれていた変更のうち**Postgresのポート絞り込み・再起動ポリシー・ログドライバのキャップはローテーションの判断と何の関係もない**——ユーザー判断を必要とせず、ローテーションのリスク（既存の暗号化済みデータが読めなくなる可能性）も一切伴わない。これらを鍵ローテーションのサインオフの背後に置いたまま待たせる理由はないため、本項目を**4a（ゲート不要）**と**4b（要ユーザー承認）**に分離する。**4aは4bの判断を待たずに独立して進めてよい。**

#### 4a. ゲート不要な硬化

- **(a) Postgresのポート公開範囲を絞る**: `docker-compose.yml`の`postgres`サービスの`ports:`（現在`"5432:5432"`、`docker-compose.yml:12-13`、全インターフェースに公開）を`"127.0.0.1:5432:5432"`（ローカルホストのみ）へ変更する。現状のままEC2等へ持ち出すと、セキュリティグループの設定次第でDBがネットワーク越しに到達可能になるリスクがある。
- **(b) llm-serviceのポート公開を完全に廃止する**: `docker-compose.yml`の`llm-service`サービスは現在`"8000:8000"`で全インターフェースに公開している（`docker-compose.yml:44-45`）。しかしllm-serviceは認証機構を持たないFastAPIサービスで、呼び出し側が渡す`api_key`をリクエストボディの平文フィールドとして受け取り、Anthropicへ転送する構造になっている（`llm-service/main.py`の複数のリクエストモデルに`api_key`フィールドが平文で存在する）。これを呼び出すのはbackendのみで、それもcomposeネットワーク経由(`http://llm-service:8000`、`application.yml:38`のデフォルト値)である。ホストにこのポートを公開する意味は元々なく、EC2等の実環境に持ち出した場合には実害のある露出になる。**`llm-service`の`ports:`ブロックそのものを削除する。**
- **(c) 再起動ポリシーの追加**: postgres/backend/llm-serviceの3サービス全てに`restart: unless-stopped`を追加する。`StuckJobResumer`は実運用下での中断/再開からの回復能力が実証済み（`docs/spec/nfr-status-2026-08.md`7章、job 37で3回の中断/再開を経て正しく完了した実測エビデンス）だが、その回復力はコンテナ自体が実際に再起動されて初めて意味を持つ——現状は`restart:`ポリシーが3サービスいずれにも設定されておらず、プロセスクラッシュ時に自動再起動しない。**ただし**、`restart: unless-stopped`が回復できるのはプロセスが実際に終了(exit)した場合のみであり、**ハングしたまま生きているプロセス**は対象外である。またCompose単体（Swarmではない）ではhealthcheckの失敗が自動的な再起動をトリガーしない——この回復保証を過大評価しないこと。
- **(d) Dockerログドライバのキャップ追加**: postgres/backend/llm-serviceの3サービス全てに`logging: {driver: json-file, options: {max-size: "10m", max-file: "3"}}`を追加する。**アプリケーションレベルのログローテーションは既に対応済み**であり（`application.yml`の`max-file-size: 10MB`・`max-history: 14`・`total-size-cap: 500MB`）、これはギャップではない。未対応なのはDockerの`json-file`ドライバが**標準出力のキャプチャそのものにキャップを持たない**点で、これはアプリケーションログとは別に重複してディスクを消費する——これが実際に手当てされていない容量増大要因である。あわせて、ビルドキャッシュレイヤ向けに`docker system prune -af --filter until=168h`を定期的（例: 週次）に実行する運用を推奨する。**なお、ディスク容量アラート等の監視/アラーティングスタックは、スケジュール稼働の単一ユーザー用ホストには不釣り合いであり、意図的に推奨しない**——増大源そのものにキャップをかけることが、このスケールに見合った対処である。
- **(e) backendのllm-serviceへの起動順依存を明示**: backendはllm-serviceを呼び出すが、現在`docker-compose.yml`の`backend`サービスの`depends_on`にはpostgresしか含まれていない（`docker-compose.yml:23-25`）。`backend.depends_on`に`llm-service`を追加する。

**完了の定義（4a）**: `docker compose ps`でPostgresのポートマッピングが`127.0.0.1:5432->5432/tcp`になっている。`docker compose ps`でllm-serviceにホスト側ポートマッピングが一切表示されない。3サービスとも`docker inspect`で`RestartPolicy.Name == "unless-stopped"`、および`HostConfig.LogConfig`が`max-size: 10m`・`max-file: 3`になっている。`backend`の`depends_on`に`llm-service`が含まれる。

#### 4b. 要ユーザー承認（§1の鍵ローテーション判断が前提）

- **(a) 環境変数の配線を追加**: `docker-compose.yml`の`backend`サービスの`environment:`ブロックに`APP_SECRET_ENCRYPTION_KEY`・`ADMIN_EMAIL`・`JOB_RETENTION_DAYS`を追加する。既存エントリ（`CPE_FULL_SYNC_ON_STARTUP: ${CPE_FULL_SYNC_ON_STARTUP:-false}`）と同じ`${VAR:-default}`形式に揃える。
- **(b) ハードコードされたAESデフォルトの撤去**: `application.yml:36`の`${APP_SECRET_ENCRYPTION_KEY:<default-literal>}`のようなフォールバック付き記法をやめ、環境変数が未設定、または依然として旧デフォルトリテラルと一致する場合に`SecretEncryptionService`が**起動時にfail fastする**ようにする。サイレントなフォールバックがこの問題をここまで長く見えなくしてきた根本原因であるため、単に「デフォルト値を新しいランダム値に差し替える」のではなく、「デフォルト値という概念自体をなくす」方向で直す。**実装方式の指定**: fail-fastの判定は、設定された鍵のSHA-256ハッシュを、退役済みデフォルト値のハッシュからなる小さなdeny-listと比較する方式で行う。**退役対象のリテラル自体をソースコードへ再度埋め込んではならない**——それはこの修正が解消しようとしている問題（デフォルトリテラルがコード中に存在すること）をそのまま再現してしまう。ハッシュ方式であれば、将来別のデフォルト値を退役させる場合もdeny-listにハッシュを1件追加するだけで済む。
- **(c) `POSTGRES_PASSWORD`のデフォルト撤去**: `docker-compose.yml:9`の`${POSTGRES_PASSWORD:-vulncheck}`、および`application.yml:8`の`${SPRING_DATASOURCE_PASSWORD:vulncheck}`はいずれも、暗号化キーと同じ「コミット済みデフォルト値」という同種の問題を抱えている。暗号化キーに適用する「デフォルトという概念自体をなくす」原則をここにも適用し、デフォルト値なしの必須環境変数として扱う。**このカテゴリの変更は既存の動作を壊すという点で暗号化キーと同種のリスク（規模はより小さい）を伴うため4bに置く。** なお現時点では、Postgresのポート絞り込み(4a)が、デプロイ後にこのDBを保護する**唯一の**制御である。
- **(d) 鍵ローテーション本体**: §1-2で述べた(a)再暗号化 vs (b)再入力依頼のいずれかを実行する。

**要ユーザー承認事項（再掲、§1-2参照）**: (b)を実行する時点で、既存の暗号化済みAPIキーをどう扱うか（再暗号化 vs 再入力依頼）を先に決めておく必要がある。

**完了の定義（4b）**: `docker-compose up`後、`APP_SECRET_ENCRYPTION_KEY`を意図的に空/退役済みデフォルト値のまま起動した場合にbackendが起動失敗する（deny-listハッシュ方式でfail fastすることをコードレビューで確認）。正しい新規キーを設定した場合は正常起動し、既存ユーザーのAPIキーが復号可能（再暗号化を選んだ場合）または再入力導線が機能する（再入力を選んだ場合）。`POSTGRES_PASSWORD`にデフォルト値なしで環境変数が必須化されている。

### ロールバック手順（項目4・項目5に関する原則）

- **composeの変更（項目4a/4b）**: `git revert`で該当コミットを打ち消し、`docker compose up -d`で再適用する。これは項目1（git init）を最初に置くべきもう一つの根拠でもある——gitがなければ`revert`という手段自体が使えない。
- **コスト台帳マイグレーション（項目5、V17）**: Flyway Community Editionには自動ロールバック機構がない。したがって、後からアプリケーションJARだけを前のバージョンへロールバックしてもスキーマ側の非互換が起きないよう、**V17は追加のみ（additive-only）とする**という設計制約を課す（詳細は項目5本文）。この制約を守っている限り、問題が起きた場合はアプリケーションJARだけを前のバージョンへ戻せば安全（追加されたテーブル/カラムは旧JARから見えないだけで、データ破壊は起きない）。スキーマ自体を戻す操作は原則行わない。

1. **スループット**: 2026-08-25の性能修正後の状態で、かつ`StuckJobResumer`による中断/再開を挟まない（デプロイ作業と重ならない時間帯に実行する）、クリーンな1,000件ジョブの壁時計計測を1本通す。`docs/spec/nfr-status-2026-08.md`3章が記録した通り、既存の唯一の1,000件実測(job 30、6時間25分)は並列化前の無効な前提下の数値であり、また同一条件の400件同士でも中断の有無だけで9倍の開きが観測された(job 36: 6分50秒 vs job 37: 1時間03分、原因は`StuckJobResumer`による3回の中断)ため、中断のないクリーンな計測がまだ1件も存在しない。
2. **静的精度**: 300件のゴールデンベンチマークセットを構築し、「識別できたか」ではなく「**正しく**識別できたか」を測定する。`docs/spec/nfr-status-2026-08.md`2章が明記する通り、直近ジョブの94.0%〜96.75%という参考値はいずれも identified-vs-correct の定義ズレを含み、目標2(95%)の正式な達成/未達判定には使えない——これは`project_three_pillar_targets`メモリが既に指摘していた「job 31's 97.7% was "identified at some confidence," not "correctly identified at 95%+ confidence"」という混同リスクと同型である。

**credential/cost gate（要ユーザー承認）**: 実際のClaude APIキーを環境へ復帰させ、1,000件のスループット計測ジョブと300件のゴールデンベンチマークを実行することは、(a) 実クレデンシャルが再び環境に入ること、(b) 実際の支出（スループット計測だけでも$5/1,000件の目標値換算でおよそ$5〜20程度、ゴールデンベンチマーク分は別途）を伴う。これは`feedback_stop_for_credentials`メモリが§1で既に要求しているのと同じ種類の明示的なユーザーのサインオフを要する事項であり、§6（未決定事項）に独立した項目として立てる（旧版では旧項目3=コスト永続化の付随言及に埋もれ、明示されていなかった）。

**前提条件（順序制約）**: Claude APIキーを`user_secrets`へ投入するのは、**§2項目4bの鍵ローテーション判断が確定した後**でなければならない——先に投入すると、まもなく無効化される可能性のある鍵で暗号化されることになり、二度目のローテーションを強いられる。

**完了の定義**: 上記2つの実測値が記録され、目標2・目標3のそれぞれについて「達成」「未達」のいずれかを初めて宣言できる状態になる（§2項目5による目標1の実測も揃えば、3本柱すべてが判定可能になる）。

## 4. 明示的に見送る事項: ステージング環境

**今は着手しない。** 理由を以下に明記する（「後で」で済ませない）。

- ステージング環境の本来の目的は「本番相当の構成に対してデプロイを予行演習する」ことである。しかし現時点で**本番環境そのものが存在しない**——IaCなし、TLS終端なし、実プロビジョニング済みホストなし、そして§1で述べた通りdocker-compose.ymlの環境変数契約は文書化されている3変数のうち3つとも実際には機能していない状態にある。「本番のコピー」を作る前に、まず本番自体が要る。
- ステージング環境を作りたくなった直接の引き金——job 36とjob 37の間で観測された400件ジョブの9倍のスループット差——は、根本原因が既に特定済みである: デプロイ作業に伴う`StuckJobResumer`の中断/再開であり、環境の違いによるものではない(`docs/spec/nfr-status-2026-08.md`3章)。これは「測定中はデプロイしない」という運用規律と、§2項目5(コスト台帳の永続化、ひいては状態が再起動をまたいで残る設計全般)で解決できる問題であり、第2の環境を作ることでは解決しない。
- なお§2項目6のマイグレーション連鎖リハーサルは、既存ホスト上・仮想ボリュームで数分だけ行う検証作業であり、本節が見送る「ステージング環境」とは別物である。両者を混同しないよう、項目6側にもその旨を明記している。
- **結論**: ステージング環境は、§2項目7(IaC + 実運用環境1つ)が実在して初めて再検討する価値が生まれる。それより前に作ることは、本番相当の対象が存在しないまま「本番相当のコピー」を作ることになり、目的を果たせない。
