# Anthropic Batch API 統合設計（2026-08-25 設計のみ・未実装）

**本ドキュメントは設計のみ。実装コードは一切含まない。** 対象は Stage1 Tier2/Tier3（`Stage1IdentificationService`）と Stage4（`Stage4WebSearchResearchService`）が行う Claude API 呼び出しを、Anthropic Message Batches API（トークン単価50%割引、レイテンシは「大半1時間以内・最大24時間」）に載せ替えるかどうか・載せ替えるならどう構成するかの検討である。

`known-limitations.md`（当時の記述）は「二相構成（Stage1のLLM呼び出しを全部まとめてバッチ送信→結果反映→Stage4のLLM呼び出しをまとめてバッチ送信）への再設計が必要」とだけ書いて2026-08-23時点で2回見送っていた。本ドキュメントはその見送りを、現行コード（2026-08-25時点、コスト是正パッチ適用済み）に対して具体的に検証し、二相構成が実際には**三相になりうる**こと、コスト側の割引適用範囲に未確認の前提があること、実行モデル自体が現状の「1回のブロッキング呼び出しで完結する」設計と根本的に相容れないことを明らかにした上で、スコープ判断（opt-in/自動/対象外）と未解決事項を整理する。

## 1. 現状アーキテクチャの要約（コード引用）

### 1-1. 同期呼び出しである理由

`llm-service/main.py:6-10` が明言している：「Requests are per-item and synchronous; the plan's Batch API cost optimization (50% discount) is deferred to a later pass since it changes the calling shape to submit-then-poll — not implemented here.」

`ResearchJobProcessingService.processJobAsync`（`ResearchJobProcessingService.java:110-169`）は、1ジョブ分のアイテムを `itemProcessingExecutor`（8並列、`AsyncConfig.java:81-90`）に投入し、`CompletableFuture.allOf(...).join()` で**全アイテムの完了をこの1回の呼び出し内でブロッキング待機**してから `job.setStatus(COMPLETED)` を書く。`JobCostBudgetService.startJobBudget`/`endJobBudget` もこの1回の呼び出しの開始・終了（`try`/`finally`）にぴったり紐づいている（`ResearchJobProcessingService.java:122,160-162`）。つまり現行実装は「ジョブの処理＝1回のブロッキング呼び出しで完結する」ことを前提にした設計であり、これは §4-3 で述べる通りバッチモード導入時の最大の障害になる。

### 1-2. Tier2/Tier3/Stage4 の発火条件（実装ベース）

| 呼び出し | 発火条件 | コスト（worst-case見積り、`JobCostBudgetService.java:61-63`） |
|---|---|---|
| Tier2（`disambiguate`） | CPE候補が2件以上（`Stage1IdentificationService.java:334`）、または単一候補の信頼度確認（`:499-521`,`:563-584`,`:638-681`） | $0.003 |
| Tier3（`webSearchIdentify`） | Tier1（レジストリ+CPE辞書）が完全に空振り（`Stage1IdentificationService.java:158-159,192`） | $0.03 |
| Stage4（`webSearchResearch`） | Stage2が0件かつ全ソースのうち最低1つは成功、かつ識別信頼度 >0.85（`ResearchJobProcessingService.java:300-322`） | $0.015 |

### 1-3. 【新規に発見した重要な事実】 Tier3 は Tier2 を内部で再度呼びうる

`Stage1IdentificationService.tryTier3`（`:192-242`）は Tier1 が完全に空振りだった場合にのみ発火するが、その内部で：

1. Claude に web_search 込みで正式名称を解決させる（LLM呼び出し#1）。
2. 解決された名称でレジストリ・CPE辞書を**再照会**（`:222-229`、ここは無料・同期・ローカル）。
3. 再照会の結果、CPE候補が2件以上あれば `resolveCandidates`（`:240` → `:318-373`）が**Tier2の`disambiguate`エンドポイントを再度呼ぶ**（`:334-363`、LLM呼び出し#2）。

つまり「Tier1完全空振り→Tier3→（再照会でCPE候補が複数）→Tier2」という**LLM呼び出しが2段階連鎖するケースが実装上存在する**。しかも2段階目（Tier2）の入力（CPE候補リスト）は1段階目（Tier3）の出力（解決済み名称での再照会結果）に**データ依存**しており、1段階目の結果が確定するまで2段階目のリクエストを組み立てられない。この連鎖の発生率（Tier3成功かつ再照会でCPE候補2件以上になる件数の割合）は測定されていない。

**この事実は「Stage1を1つのバッチにまとめて送信」という当初案（`known-limitations.md`記載）を単純には成立させない。** 詳細は §4-2 で扱う。

### 1-4. `JobCostBudgetService` の設計上の前提（バッチ導入時に問題になる点）

`JobCostBudgetService.java:28-33` のjavadocは明言している：「Deliberately in-memory rather than persisted: state only needs to live for one job's processing pass.」——これは現行の同期処理（数分〜数十分で完結）を前提にした意図的な設計判断であり、アプリ再起動をまたぐ可能性は「小さな許容できるエッジケース」として片付けられている（`StuckJobResumer` が再開時に予算を作り直すだけで、二重予算消費の可能性は許容）。バッチモードでは待機が数十分〜最大24時間に及ぶため、この前提が崩れる。詳細は §4-3。

## 2. コスト試算: バッチ割引だけでギャップは埋まるか

### 2-1. 割引適用範囲の不確実性（★最重要の未確認事項）

Tier2/Tier3/Stage4 の worst-case コスト内訳（`JobCostBudgetService.java:46-63` のコメントより）:

| 呼び出し | トークン由来コスト | web_search由来コスト（$10/1,000回） | 合計（worst-case） | web_search比率 |
|---|---|---|---|---|
| Tier2 | 全額（web_search無し） | $0 | $0.003 | 0% |
| Tier3（max_uses=2） | ~$0.006 | ~$0.02（2回） | $0.03 | **約67%** |
| Stage4（max_uses=1） | ~$0.0044 | ~$0.01（1回） | $0.015 | **約67%** |

Tier3・Stage4 のコストの**過半（約2/3）は web_search サーバーツールの従量課金**であり、トークン単価ではない。Anthropic の Batch API は Messages API のトークン単価に50%割引を適用するが、**web_search のようなサーバーツールの従量課金にも同率の割引が適用されるかどうかは、本設計時点のドキュメント調査だけでは確認できていない**。これは実装着手前に Anthropic の最新バッチ料金ページで直接確認すべき、極めて実務的だが致命的な前提である。

2つのケースで試算する:

**ケースA（web_search料金も50%割引される場合）**: Tier2/Tier3/Stage4 とも一律50%減。

**ケースB（web_search料金は割引されず、トークン分のみ50%減）**:
- Tier2: $0.003 → $0.0015（100%がトークンなので変化なし、通常割引通り）
- Tier3: $0.02（search） + $0.003（トークン半額） = $0.023（**23%減**、50%減ではない）
- Stage4: $0.01（search） + $0.0022（トークン半額） = $0.0122（**19%減**、50%減ではない）

Stage4 は支出の79%を占める最大コスト要因（§0のベースライン実測）であり、そのStage4がケースBでは19%しか減らない。**バッチの効果はケースAとBで実質2.5倍以上違う**——この一点が確認できるまで、以降のコスト計画の精度には大きな幅がある。

### 2-2. ベースラインからの到達点（推定、要再検証）

修正前実測 $0.0175/件を出発点に、(a) 2026-08-25シップ済みの発火率削減・信頼度ゲート、(b) バッチ割引、を順に適用した場合の**推定**（実測ではない）:

| 段階 | 前提 | 推定コスト/件 |
|---|---|---|
| ① 修正前実測 | — | $0.0175 |
| ② 信頼度ゲート適用後 | Stage4発火の24%が信頼度0.85以下でフィルタされる（`project_ai_cost_target`メモリの監査値） | 約 $0.0175 − (0.79×0.24×$0.0175) ≈ **$0.0142** |
| ③ さらに `max_uses` 削減後 | Stage4: 2→1（token/search概算比で単価が$0.015段階では約半分に近づく）、Tier3: 3→2（同様） | 未測定。仮に②から Stage4/Tier3 コストが単価ベースで30-40%減ると仮定すると **概算 $0.010-0.011** |
| ④-A バッチ割引（ケースA、search込み全額50%割引） | ③に50%適用 | **約 $0.005-0.0055** ≈ 目標達成域 |
| ④-B バッチ割引（ケースB、トークンのみ割引） | ③のうちStage4/Tier3のsearch分はそのまま、トークン分のみ半減 | **約 $0.008-0.009** ≈ 目標の1.6-1.8倍、未達 |

**結論**: ケースAが正しければバッチ割引単独でほぼ目標達成域に届く可能性がある。ケースBが正しければ、バッチ割引だけでは埋まらず、**発火率のさらなる削減（Tier2/Tier3/Stage4が「そもそも呼ばれない」比率を上げる）という別軸の施策が引き続き必須**である——これはタスク依頼文が最初から想定していた通りの構図であり、本設計はそれを実測値と構造で裏付けた。どちらのケースかは実装前に確認すべき最優先事項として §7 に記載する。

なお②③はいずれも「未検証」（`project_ai_cost_target`メモリ自身が要A/B検証と明記）であり、③の具体的な削減率は仮置きの概算にすぎない。実装時は必ず修正後の実ジョブでコストを再測定してから、バッチのROIを再計算すべきである。

## 3. スループットとの衝突の定量化

### 3-1. バッチのレイテンシ床（floor）

タスク依頼文および Anthropic 公式ドキュメントの通り、バッチは**アイテム数に関わらず「大半は1時間以内、最大24時間」**というレイテンシ特性を持つ。つまり1件だけをバッチ送信しても1,000件を送信しても、完了までの待ち時間の分布はほぼ同じで、**下限が実質的にゼロにならない**（Anthropic側のキュー処理次第で数分〜のことも1時間近いこともある、が「即時」は保証されない）。

### 3-2. 「二相」ではなく「最大三相」になりうる

§1-3 で示した通り、Stage1 内部に Tier3→Tier2 のデータ依存連鎖があるため、当初案の二相構成（Phase1=Stage1全体のLLM呼び出しを一括バッチ／Phase2=Stage4のLLM呼び出しを一括バッチ）は次のいずれかを選ばざるを得ない:

- **(a) 連鎖を許容し三相にする**: Phase1a（Tier2直接候補 + Tier3識別）→ 適用・無料の再照会 → Phase1b（Tier3から派生したTier2確認、対象は一部アイテムのみ）→ 適用 → Stage2（同期・無料・高速）→ Phase2（Stage4）。**最悪ケースでバッチ待機が3回**、レイテンシ床は最大 約3時間（典型ケース、各1時間として）〜最大72時間（各24時間の最悪ケースが3回連続、現実的にはまず起きないが理論上のワーストケース）。
- **(b) 連鎖対象アイテムだけ同期呼び出しに例外的に逃がす**: バッチモードのジョブであっても、Tier3で名称解決に成功しかつ再照会でCPE候補が複数出た**少数アイテムのみ**、Tier2の再呼び出しは同期（バッチ非経由・割引なし）で行う。三相化を避け、レイテンシ床を二相（最大約2時間、典型ケース）に抑える代わりに、この少数アイテム分だけ割引を諦める。

この連鎖の発生率は未測定だが、Tier3自体がすでに「Tier1完全空振り」という狭い条件でしか発火せず（発火率8%相当、§0のコスト内訳より）、そのうちさらに「再照会でCPE候補が複数」に絞られるため、**対象アイテムはジョブ全体のごく一部**と見積もられる。少数のためにレイテンシ床を1相分（最大24時間）丸ごと追加するのは割に合わないと判断し、**(b)を推奨する**——ただし発生率の実測値がない状態での判断であり、実装前に実データで裏を取るべき（§7）。

### 3-3. 目標スループットとの突き合わせ

二相構成（推奨案(b)採用、Phase1とPhase2）を前提に、AI呼び出しが1件でも発生するジョブの最短完了時間の**床**を試算する:

- 典型ケース（各バッチが1時間以内で完了）: 静的処理（数分〜十数分、既存実測ベース） + Phase1待機（最大1時間） + Stage2（数分、既存実測ベース） + Phase2待機（最大1時間） ≈ **約2時間強**。
- 1,000件/3時間の目標に対しては、2時間強のレイテンシ床＋実処理時間で**間に合う可能性はあるが、マージンが薄い**（残り約1時間弱に静的処理・Stage2・DB書き込み全部を収める必要がある）。
- ワーストケース（Anthropicのバッチが24時間かかる、「最大24時間」は稀だが公式に明記された上限）: **1回のバッチ待機だけで24時間目標を超過**——1,000件/3時間目標を完全に破壊する。

**この非対称性（典型ケースでは辛うじて収まるが、テール（尾部）が3時間目標を1桁以上超過しうる）が、依頼文が言う「genuine architectural tension」の核心である。** これは実装の丁寧さでは解決できない——Anthropic側のキュー処理速度に依存する外部要因であり、アプリ側でできるのは「バッチを使うかどうかを選べるようにする」ことと「バッチ待機中でも目に見える形でユーザーに状況を伝える」ことだけである。

**さらに重要**: たとえ「1,000件中1件だけ」がTier2/Tier3/Stage4のいずれかを必要とするジョブであっても、そのジョブ全体がバッチ待機の対象になるなら、**残り999件（静的のみ・数分で終わるはず）の結果表示までバッチの待ち時間に引きずられる**。これが §5 の「オプトイン」判断の最大の根拠になる。

## 4. アーキテクチャ設計

### 4-1. 新しいジョブステータス

現行 `research_jobs.status`: `PENDING` / `PROCESSING` / `COMPLETED` / `FAILED`（`ResearchJob.java:23-26`、`database-schema.md:29`）。

バッチモード用に追加が必要な状態（マイグレーション番号は次が空いている `V11` から、`database-schema.md:9-18` の採番規則に合わせる）:

| 新ステータス | 意味 | 遷移元 | 遷移先 |
|---|---|---|---|
| `WAITING_BATCH_PHASE1` | Stage1のTier2/Tier3リクエストをAnthropicバッチへ投入済み、結果待ち | `PROCESSING`（静的Tier1完了後） | `PROCESSING`（Phase1結果適用後） |
| `WAITING_BATCH_PHASE2` | Stage4リクエストをバッチ投入済み、結果待ち | `PROCESSING`（Stage2完了後） | `COMPLETED` |
| `BATCH_FAILED`（検討） | バッチ全体がAnthropic側でexpired、または結果取得が一定回数失敗 | `WAITING_BATCH_PHASE1`/`2` | `FAILED`、または静的結果のみでの`COMPLETED`（要判断、§7） |

`research_jobs` に追加が必要な列（提案、要レビュー）:
- `batch_mode BOOLEAN NOT NULL DEFAULT false`（§5のオプトインフラグ）
- `batch_phase1_id VARCHAR`（Anthropicのバッチジョブid、null許容）
- `batch_phase2_id VARCHAR`
- `batch_submitted_at TIMESTAMPTZ`（タイムアウト監視・UI表示用）

`research_job_items` 側は既存の `PENDING`/`IDENTIFIED`/`UNIDENTIFIED`（`ResearchJobItem.java:22-24`）をそのまま使い、新たに「このアイテムはバッチのどのリクエストに対応するか」を引くための列を追加する（提案）: `pending_batch_custom_id VARCHAR NULL`（Anthropicの`custom_id`、バッチ結果JSONLとの突合キー）。アイテムのステータス自体は「バッチ待ち」を独立の値にはせず、ジョブ側の `WAITING_BATCH_*` で表現する（アイテム単位では「まだPENDINGのまま、ただしバッチ結果待ち」で十分——既存の「PENDINGのみ再処理する」という`ResearchJobProcessingService`の再開安全性（`:104-109`）とも整合する）。

### 4-2. フェーズ構成（§3-2の推奨案(b)を採用）

1. **静的フェーズ（現行のTier1相当、同期・無料・既存実装のまま）**: 全アイテムに対しレジストリ照合＋CPE辞書照合を実行。Tier2直接候補（CPE候補2件以上）とTier3対象（Tier1完全空振り）を仕分ける。
2. **Phase1バッチ投入**: Tier2直接候補アイテムの`disambiguate`リクエストと、Tier3対象アイテムの`web-search`（identify）リクエストを、**1つのAnthropicバッチにまとめて**投入（同一バッチ内に異なるエンドポイント相当のリクエストを混在させて問題ない——Batch APIは個々のMessages API呼び出しパラメータの集合を受け付けるだけで、呼び出し元がどのビジネスロジックのために送ったかは関知しない）。ジョブは `WAITING_BATCH_PHASE1` へ。
3. **Phase1結果適用**: バッチ完了後、Tier2の結果はそのままCPE確定に反映。Tier3の結果は無料の再照会（レジストリ＋CPE辞書、`Stage1IdentificationService.java:222-229`相当）を行い、再照会でCPE候補が複数出た少数アイテムは**同期で**Tier2の`disambiguate`を呼ぶ（§3-2の(b)、割引なしだが対象は少数）。
4. **Stage2（既存のまま、同期・無料）**: 識別済み全アイテムに対しNVD/OSV/CVE.org（GHSAは既に除外済み）を並行照会。
5. **Phase2バッチ投入**: Stage2が0件かつ信頼度>0.85のアイテムのStage4リクエストをバッチ投入。ジョブは `WAITING_BATCH_PHASE2` へ。
6. **Phase2結果適用・ジョブ完了**: `COMPLETED`。

### 4-3. 実行モデルの変更（最大の実装インパクト）

現行の `processJobAsync`（`ResearchJobProcessingService.java:110-169`）は「1回の呼び出しがジョブの生存期間全体をブロッキングで抱える」設計。バッチモードでは、Phase1/Phase2投入後にこの呼び出しを**即座にreturnさせ**、スレッドを解放する必要がある（さもなくば `researchJobExecutor`——コア4・最大8スレッド、`AsyncConfig.java:25-36`——が数十分〜時間単位でスレッドを1本占有し続け、他ジョブの受け入れを圧迫する）。

これは「ジョブの処理が1メソッド呼び出しで完結する」という現行の前提そのものを壊す。バッチモードでは新たに、**外部（Anthropic）のバッチステータスを定期ポーリングし、完了していれば次フェーズへ進める常駐コンポーネント**が必要になる——設計としては `StuckJobResumer`（起動時に一度だけ`PROCESSING`ジョブを拾う、`StuckJobResumer.java`）とは別物で、`@Scheduled` によるポーリングサービス（例: `BatchStatusPollerService`、数分間隔でAnthropicの `batches.retrieve(batchId)` を叩き、`ended` になっていれば結果を取得してPhase適用処理を呼ぶ）が新設コンポーネントとして必要。

**`JobCostBudgetService` への影響（構造的な不整合）**: 同サービスは「1ジョブの処理パス（＝1回の`processJobAsync`呼び出し）の間だけ生きればよい」ことを前提にした意図的なin-memory設計（`JobCostBudgetService.java:28-33`）。バッチモードでは `startJobBudget`/`endJobBudget` の対応する「1回の呼び出し」という単位が消える——予算はPhase1投入時に確保し、Phase2適用完了まで（数十分〜数時間、複数回のアプリ再起動をまたぎうる期間）生き続ける必要がある。現行のin-memory `Map<Long, BigDecimal>` はアプリ再起動で消える。同期ジョブでは「再起動をまたぐのは稀な運用事故」として許容されていた（`StuckJobResumer`のjavadocが明言）が、バッチモードでは「数十分〜24時間待つ」ことが**通常運用そのもの**であり、その間に1回もデプロイ・再起動が起きない保証はない。**この設計不整合は必ずどちらかの形で解消する必要がある**（DB永続化に変える／バッチモードのジョブだけ別のコスト追跡機構にする、の二択、詳細は§7の最重要オープン事項）。

### 4-4. ユーザー向けの進捗表示

既存の `jobs/detail.html:5,11` は `PENDING`/`PROCESSING` の間、5秒ごとの `meta http-equiv="refresh"` で自動更新する素朴な仕組みを持つ。`WAITING_BATCH_PHASE1`/`PHASE2` もこのポーリングの対象に加えるだけで、**技術的には最小変更で「待っています」という状態を見せ続けられる**——ただし現行の文言（5秒で終わるであろう処理を想定した表現）は「バッチは通常1時間以内、最大24時間かかりえます」という期待値を明示的に伝える文言に差し替える必要がある。特に、静的フェーズ・Stage2フェーズはすでに完了して個別アイテムの結果が閲覧可能な状態で「一部の項目はAI調査待ちです」と部分結果を見せられるようにするか（既存の「アイテムごとの結果表示」テーブルはこのUXと相性が良い、詳細は§7）、ジョブ全体を「まだ何も見せない」ままにするかはUI設計判断として残る。

### 4-5. 失敗モードへの対応

Anthropic Batch APIの失敗モード（バッチ全体／個別リクエスト単位）:

- **バッチ全体が `expired`**: 24時間以内に完了しなかった場合。この場合、未処理分の個別リクエスト結果は取得できない。対応: そのフェーズを対象アイテムについて**現行の「AIキー未設定時と同じ劣化動作」**（Tier2なら先頭候補採用、Tier3なら未識別のまま、Stage4なら発見なしのまま）にフォールバックさせ、`researchIncompleteReason` 相当の理由コード（既存の `SOURCES_FAILED`/`IDENTIFICATION_TOO_WEAK` と同じ考え方、`ResearchJobItem`）を新設して記録する。
- **個別リクエストが `errored`/`expired`（バッチ自体は`ended`）**: 該当アイテムのみ同上の劣化動作。バッチ内の他アイテムの結果は正常に使う——これは現行コードがすでに持っている「1アイテムの失敗が他アイテムを巻き込まない」設計思想（`processItemSafely`, `ResearchJobProcessingService.java:222-238`）とそのまま接続できる。
- **ポーリングがバッチIDを見失う**（アプリ再起動でメモリ上の追跡状態を失う等）: §4-3の永続化の議論と同じ問題。`batch_phase1_id`/`batch_phase2_id` をDB列として持たせる提案（§4-1）はこれを解決するための最小限の手当て——起動時に `WAITING_BATCH_*` のジョブを拾い、保存済みのバッチIDでAnthropicに再照会するロジックを `StuckJobResumer` 相当のコンポーネントに追加すればよい。

### 4-6. `JobCostBudgetService` との統合（予約タイミングの変更）

現行は「Claudeを呼ぶ直前に`tryReserve`、レスポンスが返ったら`reconcile`」という単純な対応（`Stage1IdentificationService.java:197,335-357`等）。バッチモードでは:

- **予約はバッチ投入時に一括**: Phase1/Phase2に含める各アイテムについて、投入前に`tryReserve`相当を呼び、予約が通ったアイテムだけをバッチペイロードに含める（通らなかったアイテムは最初からバッチに乗せず、劣化動作に回す——現行の「予算が尽きたら以降のAI呼び出しは全部スキップ」という設計思想と一致）。
- **確定精算はバッチ結果取得時に一括**: 各アイテムの`custom_id`ごとに実測トークン数・web_search回数を取り出し、`reconcile`を呼ぶ。これは既存の`reconcile`のシグネチャ（予約額と実測額のペア、`JobCostBudgetService.java:163-171`）をそのまま使い回せる——**この部分は構造変更が小さい**。
- 変更が大きいのは「予約から精算までの時間が数秒から数十分〜時間へ伸びる」ことそのもの（§4-3の永続化問題と同根）。

## 5. スコープ判断: opt-in per-job を推奨

### 5-1. 選択肢

- **(A) デフォルトのAI呼び出し経路を全てバッチに置き換える**: §3-3の通り、AIを1件でも必要とするジョブ全てに数十分〜最大24時間のレイテンシ床が乗る。1,000件/3時間の目標を（テールケースで）壊しうる。**却下**——依頼文の言う「genuine tension」を無視することになる。
- **(B) ジョブサイズによる自動切り替え（例: N件超で自動バッチ）**: 一見合理的だが、レイテンシ床（バッチの待ち時間）はアイテム数に依存しない（§3-1）ため、「サイズが大きいほどバッチが有利」という直感は**コスト面では正しいが、レイテンシ面では成立しない**——1,000件のジョブでも10件のジョブでも、バッチの待ち時間はほぼ同じ1時間床である。むしろサイズが大きいジョブほど「静的フェーズ・Stage2フェーズだけで元々時間がかかる」ため、バッチの1時間床が相対的に許容しやすくなる、という意味では自動切り替えの根拠は残る。ただし「何件からバッチにするか」の閾値は、AI発火率（Tier2/Tier3/Stage4がそもそも何件で発火するか）にも依存し、静的な件数閾値だけでは決め切れない。
- **(C) opt-in（CSVアップロード時にユーザーが「速い（同期）」/「安い（バッチ、待ち時間あり）」を選択）**: 依頼文で言及されている前回セッションの推奨案。ユーザー自身が「今すぐ結果が欲しい少数件のジョブ」と「コストを最小化したい大量件のジョブ」を最もよく知っている——このアプリの利用シーン（インストール前の事前確認、`README.md:12`）は即時性が重要な場面と、まとめて棚卸しする場面の両方がありうる。

**推奨: (C) を採用し、将来的に(B)の閾値ベースの「バッチを推奨表示する」（強制ではなく）UIヒントを重ねる。** 理由:

1. §3-3で示した通り、バッチのレイテンシは**テールで3時間目標そのものを破壊しうる**外部要因であり、これをユーザーの同意なしにデフォルト経路へ組み込むのはリスクが大きい。
2. 現在のUI（CSVアップロードフォーム、`jobs/new.html`）はすでにユーザー入力を受け付ける画面であり、チェックボックス1つ（「コスト優先モード（結果が出るまで数十分〜最大24時間かかることがあります）」）を足す変更コストは小さい。
3. コスト目標達成の主軸は§2の通り「発火率削減（信頼度ゲート・`max_uses`削減、既に一部実装済み）」であり、バッチはそれでも埋まらないギャップ（ケースB想定）を埋める**追加の、かつジョブ側の同意がある場合限定の**手段として位置づけるのが、依頼文の「バッチの50%割引が主要な梃子であり、それでも埋まらない分は発火率削減という別軸」という整理とも一致する。

## 6. 未解決 / 未決定事項

実装着手前に解決すべき事項を優先度順に列挙する。

1. **【最優先・実装前に必ず確認】 Anthropic Batch API の割引が `web_search` サーバーツールの従量課金（$10/1,000回）にも適用されるか。** §2-1のケースA/Bでコスト到達点が2.5倍以上変わる。Anthropicの最新バッチ料金ドキュメント／実際に少量のバッチを投げてinvoiceを確認する、のいずれかで確認する必要がある。
2. **`JobCostBudgetService` の永続化問題（§4-3）。** in-memoryのまま「バッチモードのジョブだけ別の仕組みで追跡する」か、全ジョブ共通でDB永続化に作り替えるか。後者は影響範囲が全AI呼び出しサイトに及ぶ、より大きな変更になる。**本ドキュメントの中で最も“アーキテクチャ判断”らしい判断であり、次のセクションで単独の論点として立てる。**
3. **Tier3→Tier2連鎖（§1-3, §3-2）の実発生率。** 未測定。§3-2で推奨した「連鎖対象は同期に逃がす」判断の妥当性は、この発生率が本当に少数かどうかに依存する。
4. **バッチ待機中の部分結果UI（§4-4）。** 静的フェーズ・Stage2フェーズの結果はバッチ完了前から確定しているが、それを「一部完了」として見せるか、ジョブ全体を「処理中」表示のままにするかは未決定。前者はUX上望ましいが、既存の`jobs/detail.html`のテーブルは「ジョブが完了するまで一覧全体が更新され続ける」ことを前提にしたテンプレート構造で、部分表示のための状態設計（アイテムごとに「静的結果確定・AI結果待ち」を示す第3の表示状態）が追加で必要になる。
5. **`WAITING_BATCH_*` 中にジョブをキャンセルする経路の要否。** 現行UIにジョブキャンセル機能はない（コントローラ一覧、`architecture.md:19-33`に該当ルートなし）。バッチが最大24時間かかりうる以上、ユーザーがキャンセルしたくなる場面は現行の同期ジョブより明らかに増える。Anthropic側は進行中バッチのキャンセルAPIを持つため技術的には可能——UI/UXとしてこの機能を今回のスコープに含めるかは未決定。
6. **信頼度ゲート・`max_uses`削減の効果の実測（§0既出、`project_ai_cost_target`メモリの既存オープン事項の再掲）。** バッチのROI計算自体がこの未測定値の上に乗っているため、バッチ実装前にまず修正後の実ジョブでコストを再測定すべき、という優先順位の問題でもある。

### 6-1. 単独で立てるべき論点: `JobCostBudgetService` を作り替えるか、バッチ専用の別機構にするか

- **選択肢α: `JobCostBudgetService`自体をDB永続化に作り替える。** 全AI呼び出しサイト（Tier2/Tier3/Stage4、同期・バッチ問わず）が同じ一貫した仕組みでコスト追跡される。実装コストは高い（全呼び出しサイトの変更、トランザクション設計、同時実行時の整合性——現行はConcurrentHashMap+synchronizedで簡潔に解決している排他制御をDBレベルでやり直す必要がある）。
- **選択肢β: バッチモードのジョブだけ、Phase投入時にDBへ予約額を書き込み、Phase適用時に実測額へ更新する専用の小さな仕組みを追加する。** 同期モードの既存コード・既存テストには触れない。ただし「同期とバッチが混在する将来のジョブ」（例: 一部アイテムだけバッチ、残りは即座に同期——今回は§5でopt-inをジョブ単位にしたので発生しないが、将来的に閾値ベース(B)へ拡張する場合は起きうる）が出てきた場合、コスト追跡の仕組みが二重化して一貫性を保つのが難しくなる。

**本ドキュメントでは判断を確定させない。** 影響範囲・リスクの非対称性（αは広く触るがシンプルで将来に強い、βは局所的だが将来の二重化リスクを残す）から、実装着手前にシニアレビューでの判断を仰ぐべき論点として次の最終節に記載する。

## 7. まとめ: 最も判断を仰ぎたい論点

設計を通して見えた最大のアーキテクチャ上の緊張は、**「ジョブの処理は1回のブロッキング呼び出しで完結する」という現行の実行モデル（`processJobAsync`が予算の開始・終了・スレッド占有を1つのメソッド呼び出しの生存期間に紐づけている、`ResearchJobProcessingService.java:110-169`、`JobCostBudgetService.java:28-33`）が、バッチモードの「投入→解放→分単位でポーリング→数十分〜24時間後に再開」という非同期モデルと構造的に相容れない**ことである。これはStage4の発火条件やコスト単価のような調整可能なパラメータの話ではなく、ジョブという概念そのものの生存期間モデルに関わる。

この一点に対して二つの現実的な対応があり、トレードオフが明確に異なる（§6-1）:

- **α: `JobCostBudgetService`をDB永続化に作り替える**（広く触るが、将来の拡張——閾値ベースの自動バッチ化や、同期/バッチ混在ジョブ——に強い一貫した基盤になる）
- **β: バッチモード専用の小さな追跡機構を別に足す**（今回のopt-inスコープには最小の変更で済むが、思想の異なる2つのコスト追跡機構が並存することになる）

これに加えて、実装着手前に必ず確認すべき事実ベースの前提（§6-1)が一つある: **Anthropic Batch APIの割引がweb_searchサーバーツール料金にも及ぶかどうか**——これが判明しない限り、バッチ単独でコストギャップがどこまで埋まるかの試算（§2）の幅は2.5倍以上残ったままになる。
