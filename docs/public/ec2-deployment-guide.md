## 1. デプロイ前にユーザー側で決めておくこと

1. **インスタンスサイズ・リージョン**: `project_vuln_research_server`メモリに`t4g.medium`・月額約$9.75という見積もりがあるが、「us-east-1ベースの概算+東京上乗せ、未確認」と記載されている。実プロビジョニング前にAWS料金計算ツールで再確認すること。
2. **稼働スケジュール**: 常時稼働か、スケジュール稼働(例: 10:00-15:00)か。後者ならコスト削減になるが、EC2の自動起動/停止の仕組み(Lambda+EventBridge等)は別途必要——この構築自体もAWS操作を伴うためユーザー側の作業。
3. **TLS/リバースプロキシ**: Caddy or Apacheを想定(`project_vuln_research_server`メモリで既に合意済み、ユーザー自身のタスク)。ドメイン名の用意もこの時点で必要。
4. **暗号化済みAPIキーの扱い**: 既存のローカル環境で`user_secrets`テーブルにAPIキーが暗号化保存されている場合、EC2側は新規の`APP_SECRET_ENCRYPTION_KEY`を使うことになるため、**ローカルの暗号化データをそのまま持ち込んでも復号できない**。(a)DBごと移行して同じ鍵を使う、(b)EC2側はクリーンスタートでユーザーに再入力してもらう、のどちらにするか事前に決めておくこと。

## 2. デプロイ手順(EC2インスタンスにSSH接続できる状態から)

1. **Dockerのインストール**: Amazon Linux 2023やUbuntuの公式手順でDocker Engine + Docker Composeプラグインを導入する(AWS操作ではなくOS内部の作業なので、ユーザーが実施する場合はこちらの手順書に従って進めてよい)。
2. **リポジトリの取得**: `git clone`でこのリポジトリをEC2上に配置する(公開リポジトリなので認証不要)。
3. **`.env`の作成**: `.env.example`をコピーし、以下を必ず設定する(いずれもデフォルトなし、未設定だとbackendが起動時にfail-fastする設計)。
   - `POSTGRES_PASSWORD`
   - `APP_SECRET_ENCRYPTION_KEY`(上記1-4の判断に応じて、新規生成 or 既存環境と同じ値)
   - `ADMIN_EMAIL`
   - `JOB_RETENTION_DAYS`(任意、デフォルト30)
   - **`SESSION_COOKIE_SECURE=true`(2026-08-30追加、TLS導入後に必須)**: セッションCookieの`Secure`属性を制御する環境変数。デフォルト`false`(ローカル開発・TLS無し環境向け)。**下記手順7でTLS終端を設定した後は、必ず`true`に変更すること**——`false`のままだとセッションCookieが平文HTTP経由でも送信されうる。
4. **`docker-compose.yml`のハードニング(推奨、EC2投入前に対応しておくと安全)**: 上記0章の「未実施」3項目——`restart: unless-stopped`(3サービス)、ログドライバのキャップ(`max-size: "10m"`, `max-file: "3"`)、`backend.depends_on`への`llm-service`追加——は、コード変更を伴う軽微な修正なのでEC2投入前に`test`→`staging`→`master`の通常フローで済ませておくことを推奨する(詳細はinfra-rollout-plan.md§2項目4a参照)。
5. **起動**: `docker compose up -d`。
6. **マイグレーション適用の確認**: 初回起動時にFlywayが自動的に全マイグレーション(V1〜最新)を空のDBへ適用する。ログで失敗が無いことを確認する。**この「空ボリュームからの通し適用」は、infra-rollout-plan.md項目6が指摘する通り、これまで一度も検証されたことがない**——EC2への初回デプロイが事実上その初回検証になる。可能であれば、EC2投入前にローカルの使い捨てボリュームで一度リハーサルしておくことを推奨する。
7. **TLS/リバースプロキシの設定**(ユーザー自身のタスク、上記1-3で決めた構成に従う)。設定完了後、`docker-compose.yml`のbackendの`ports:`を`"8080:8080"`から`"127.0.0.1:8080:8080"`へ変更し、リバースプロキシ経由以外の直接アクセスを塞ぐこと(**これを忘れるとTLSをバイパスして8080へ直接到達できてしまう**)。
8. **動作確認**: ブラウザでCSVアップロード〜ジョブ実行の一連の流れが動くことを確認する。

## 3. 運用上の考慮事項

- **DBサイズ10GBハードキャップ**: 同期系ジョブの実行前後で`SELECT pg_size_pretty(pg_database_size('vulncheck'));`を確認する運用を、EC2上でも継続すること。
- **`vulncheck_test`ロールを本番到達可能な環境で絶対に作らないこと**: `known-limitations.md`に記載の通り、このロール(パスワード`vulncheck_test`固定、リポジトリに平文記載)はローカル開発専用。EC2上でテストスイートを実行する運用は想定しない(CI/CD構築後、CI環境側で実行する設計にすること)。
- **llm-serviceの認証**: 認証機構を持たず、backendからのcompose内部通信のみを前提とした設計。`llm-service`のポートは絶対にホストへ公開しないこと(現状既にポート非公開設定済み、変更しないこと)。
- **バックアップ**: `pg_dump`によるバックアップ/リストア手順を、EC2投入後できるだけ早期に確立すること(infra-rollout-plan.md項目3)。特に`user_secrets`テーブルは他に一次情報源がなく、失うとユーザーにAPIキー再入力を強いることになる。
- **コスト**: `APP_COST_CAP_PER_ITEM_USD`(デフォルト$0.005=$5/1,000件)の上限設定は環境変数で上書き可能。実キー投入前に必ず値を確認すること。APIクレジット補充ができない制約があるプロジェクトなので、実キーをEC2環境に投入するタイミング自体、慎重に判断すること。
- **CI/CDは未着手**: 現状、EC2へのデプロイは手動(`git pull` + `docker compose up -d --build`)になる。自動デプロイパイプラインが無いことを踏まえ、デプロイ手順書(本ドキュメント)を都度手動で辿ることになる。
